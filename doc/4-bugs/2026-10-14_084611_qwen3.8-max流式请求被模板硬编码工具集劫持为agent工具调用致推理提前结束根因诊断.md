# qwen-3.8-max 流式请求被模板硬编码工具集劫持为 agent 工具调用、致推理「一小段就停止」根因诊断

## 一、问题描述

- **现象**：会话 `e182eda1-887a-4f35-a02f-900ae31b7bc8` 使用 `qwen-3.8-max` 请求推理时，只推理一小段就停止，把控制权交回用户继续提问，感觉完全没推理完成就先行结束。
- **用户判断**：怀疑是 `qwen-3.8-max` 模型本身的问题，且强调「我们其他模型不会这样」。
- **结论（本诊断）**：**不是模型问题，是插件实现缺陷**。qoder 系插件的请求模板 `baseprompt.json` 硬编码了 Qoder CLI 的 **14 个 agent 工具**与 agent 会话上下文，而 `buildQoderBody` 对 `tools` 字段**零处理**；上游因此把每一次普通问答都当 agent 任务处理，模型「先思考 → 调用 `Bash`/`Glob` 看代码 → `finish_reason=tool_calls` 收尾」，下游客户端没有对应工具执行回路，表现为「推理一小段就停、等你继续说」。

## 二、证据链（生产实测）

生产插件版本：`qoderwork-provider-v0.9.35`、`qoder-ai-provider-v0.1.15`（`/CLIProxyAPI/plugins/linux/amd64/`，2026-10-14 01:09）。

### 2.1 症状基线：`qmodel_38max` 记录呈现「有小输出但被判定成功」

`token-usage-feed.ndjson` 中 `model":"qmodel_38max"`（alias `Qwen3.8-Max`）共 151 条，按「失败标记 × 耗时量级 × 输出 token」交叉统计：

| failed | 耗时量级 | 输出 | 条数 |
|---|---|---|---|
| true | 10–60s | **0** | 149 |
| true | >60s | **0** | 2 |
| false | 10–60s | >0 | 17 |
| false | >60s | >0 | 7 |

两类症状并存：

- **`failed=true` + `output_tokens=0`（151 条中的 151 条全部）**：上游零字节关流，插件记为 `upstream stream closed before first payload`（`qoderwork/stream.go:363-374` 的 `!emitted` 分支）。这是**并发的另一类故障**（空流），与本次现象不同。
- **`failed=false` + `output_tokens>0`（24 条）**：插件认为成功、下游收到内容——但输出 token 分布极度异常：

```
out: 26, 54, 102, 103, 114, 121×2, 129, 133, 143, 145, 173, 204, 400, 427   ← 24 条中的 16 条
out: 1075, 3086, 5077, 5634, 10765, 15225                                    ← 少量正常长输出
```

即：**绝大多数「成功」请求的输出只有几十到几百 token**，与「分三部分详细分析、每部分 300 字」这类正常任务量级（数千至上万 token）相差一到两个数量级。这与用户描述的「推理一小段就停止」完全吻合。

补充：近 24h 日志中 `model=Qwen3.8-Max` 共 281 次、`failed=true` 132 次（`usage.handle` 口径），其中 `err=upstream 200: 112: {"pricingUrl":"https://qoder.com.cn/pricing?client=qoder"}` 共 24 条（16 条 `qoder-ai-provider` + 8 条 `qoderwork-provider`）——该 112 为上游业务错误码，属独立故障线，不解释本现象。

### 2.2 决定性实测：非流式正常，流式被工具调用劫持

同一模型、同一 prompt、仅切换 `stream`：

| 轮次 | 请求形态 | 帧数 | content 帧 | reasoning 帧 | **tool_calls 帧** | finish_reason | 工具名 |
|---|---|---|---|---|---|---|---|
| A | `stream:true`，同 prompt | 45 | 6 | 13 | **23** | **`tool_calls`** | `Bash` |
| B | `stream:false`，同 prompt | — | 1（聚合） | — | 0 | `stop` | — |

- 非流式（B）：返回**完整正文 20908 字节**、`finish_reason=stop`，内容为完整的「G/M/P 三部分」分析——**模型能力完全正常**。
- 流式（A）：只有 6 帧 content（累计 109 字符），其余全是 `reasoning_content` 与 `tool_calls` 增量，最后 `finish_reason=tool_calls` 结束。

流式那次的 content 原文（决定性）：

```
data: {"choices":[{"delta":{"content":"我先确认本机"}...
data: {"choices":[{"delta":{"content":"是否有 Go 源码"}...
data: {"choices":[{"delta":{"content":"，这样可以给出精确"}...
data: {"choices":[{"delta":{"content":"的 `file"}...
data: {"choices":[{"delta":{"content":":line` 引用"}...
data: {"choices":[{"delta":{"content":"。\n\n"}...
...
data: {"choices":[{"delta":{},"finish_reason":"tool_calls","index":0}]}
```

紧接其后的是 23 帧 `tool_calls` 增量，合并后为：

```json
{"id":"call_3f539d5a12d34e80b99e595e","type":"function","index":0,
 "function":{"name":"Bash","arguments":"{\"command\": \"go version 2>&1; go env GOROOT\"}"}}
```

**判读**：模型的「我先确认本机是否有 Go 源码，这样可以给出精确的 `file:line` 引用」是**标准的 agent 工具前置声明**，随后调用 `Bash` 去探测环境，然后以 `tool_calls` 结束本轮——它认为任务尚未完成，等着工具执行结果回来继续。而下游没有这条回路，会话就停在半截。

**关键事实：这次请求我完全没有传 `tools` 字段。** 工具从何而来，见 2.4。

### 2.3 因果实验：注入「禁止调用工具」约束 → tool_calls 归零、正文完整

同 prompt，唯一变量是用户消息末尾追加「不要调用任何工具，直接凭你的知识回答，不要尝试访问文件系统」：

| 组 | 追加约束 | 帧数 | content 帧 | reasoning 帧 | **tool_calls 帧** | 正文总字符 |
|---|---|---|---|---|---|---|
| A | 无 | 45 | 6 | 13 | **23** | 109 |
| B | 有 | 2358 | **639** | 1714 | **0** | **7485** |

**这是决定性因果证据**：抑制「调用工具的倾向」后，同一模型在流式下输出 2358 帧、7485 字符完整正文、`tool_calls` 归零。说明「提前结束」的成因是**工具调用倾向被激活**，而非模型推理能力不足、也非 token 预算不足。

### 2.4 工具集来源证明：模型自省列出的工具 = 模板硬编码的 14 个

请求「逐条列出你当前可用的所有工具名称」，`qwen-3.8-max` 返回：

```
- AskUserQuestion
- Bash
- BashOutput
- Edit
- Glob
- Grep
- ImageGen
- KillBash
- Read
- Skill
- Task
- TodoWrite
- WebFetch
- WebSearch
- Write
```

对照 `qoderwork/baseprompt.json`（`qoder-ai/baseprompt.json` 逐行同构）的 `tools` 数组：

```
['Bash','BashOutput','Edit','Glob','Grep','ImageGen','KillBash','Read',
 'Skill','Task','TodoWrite','WebFetch','WebSearch','Write']   ← 14 个
```

**逐项完全一致**（`AskUserQuestion` 为 system prompt 文本提及、未列入 tools 数组，故为 14+1）。

排除「模型凭系统提示词猜出工具名」的可能：`BashOutput` / `KillBash` / `ImageGen` **三个名字在 12324 字符的 system prompt 中一次都没出现**，只存在于 `tools` 数组描述里——模型能逐字报出它们，证明 `tools` 数组**真实注入上游并被模型感知**。

对照组：同探针下 `glm-5.3` 无任何输出（该模型不走 qoder 系插件，见 2.5）。

### 2.5 同插件其他模型对照与「为什么只有 qwen3.8-max 明显」

- `glm-5.3` 在本轮 A/B 中表现正常（1812 帧、1808 content 帧、`finish=stop`），原因见 feed：`"provider":"traework-provider"` —— **它由 traework 插件承载，根本没经过 qoder 系插件**，因此不受 `baseprompt.json` 影响。用户「其他模型不会这样」的观察，本质是「其他模型走了别的 provider」。
- 同插件（qoder 系）其他模型实测：`qwen-3.8-flash` 同样触发（19 帧 tool_calls、`finish=tool_calls`、用 `Bash`+`Glob`）。

| 模型 | 承载插件 | tool_calls 帧 | finish | 用到的工具 |
|---|---|---|---|---|
| `qwen-3.8-max` | qoderwork / qoder-ai | 15–23 | `tool_calls` | `Bash`,`Glob` |
| `qwen-3.8-flash` | qoderwork / qoder-ai | 19 | `tool_calls` | `Bash`,`Glob` |
| `glm-5.3` | **traework** | 0 | `stop` | — |

即「触发工具调用」是 **qoder 系插件全模型共有的缺陷**，只是 `qwen3.8-max` 的 agentic 倾向最强、工具调用成功率最高，故症状最稳定、最刺眼（4/4 复现）。

## 三、根因

### 3.1 源码锚点

**（1）模板硬编码 14 个 agent 工具与 agent 会话上下文** —— `qoderwork/baseprompt.json`（`qoder-ai/baseprompt.json` 同构）：

```json
{
  "agent_id": "agent_common",
  "session_type": "qodercli",
  "chat_task": "FREE_INPUT",
  "tools": [ /* 14 个：Bash/BashOutput/Edit/Glob/Grep/ImageGen/KillBash/Read/Skill/Task/TodoWrite/WebFetch/WebSearch/Write */ ],
  "messages": [
    {"role":"system","content":"You are Qoder, an interactive CLI tool that helps users with software engineering tasks. ...（12324 字符，含 `# Tool usage policy`、`# Code References` 等段落）"}
  ]
}
```

system prompt 内与本次现象直接相关的两段：

```
# Tool usage policy
- When doing file search, prefer to use the Task tool in order to reduce context usage.
- You should proactively use the Task tool with specialized agents when the task at hand matches the agent's description.

# Code References
When referencing specific functions or pieces of code include the pattern `file_path:line_number` ...
```

「主动用工具」「引用必须给 `file:line`」——这两条正是模型「先去 `Bash` 探本机 Go 版本、再 `Glob` 找源码」的直接诱因。

**（2）`buildQoderBody` 对 `tools` 零处理** —— `qoderwork/body.go:153-237`（`qoder-ai/body.go:153-237` 同构）：整个函数只改写 `request_id`/`session_id`/`stream`/`model_config.key`/`parameters.max_tokens`/`chat_context.text`/`messages`/`business`，**从未触碰 `base["tools"]`**，也从未调整 `agent_id` / `session_type`。全仓 grep `'"tools"'`、`tool_choice`、`ToolChoice`、`Tools ` 在两个插件内**零命中**。

因此模板的 14 个工具与 agent 上下文**无条件、每请求**上行。

**（3）客户端工具被静默丢弃** —— `qoderwork/body.go:127-133`：

```go
type openAIRequest struct {
	Model           string          `json:"model"`
	Messages        []openAIMessage `json:"messages"`
	Stream          bool            `json:"stream"`
	MaxTokens       int64           `json:"max_tokens"`
	ReasoningEffort string          `json:"reasoning_effort"`
}
```

**没有 `Tools` / `ToolChoice` 字段**。客户端即使声明了工具，也在解析时被丢弃，无法覆盖模板工具集——形成「插件单方面替客户端声明了 14 个它不认识的工具」的双向错配：上游按 agent 模式作答，下游没有这些工具的执行回路。

### 3.2 为什么表现为「提前结束、等你继续」

模型视角：收到「你是 Qoder CLI，有 Bash/Glob/Read…，引用要给 file:line」的上下文 → 判定这是编码任务 → 先输出一句编排语（「我先确认本机是否有 Go 源码」）→ 发出 `Bash` 工具调用 → 以 `tool_calls` 结束本轮，等待工具结果。

客户端视角：它从未声明过 `Bash`/`Glob`，无从执行，也无从回传结果；收到 `finish_reason=tool_calls` 后本轮终止，界面回到等待输入态。

两侧认知差 = 用户看到的「推理一小段就停」。

### 3.3 次级发现（非本次主因，记录待办）

1. **`model_config.is_reasoning` 硬编码 `false`**：模板中 `model_config.is_reasoning` 与 `chat_context.extra.modelConfig.is_reasoning` 均为 `false`，而真实上游模型表 `models_list.json` 中 `qmodel_preview`（Qwen3.8-Max-Preview）为 `is_reasoning: true`；Go 代码只改 `key`、从不改写该标志。
   **但实测中 `reasoning_content` 正常流出**（901/1714 帧），说明上游按真实模型规格而非该标志行为——故**不是本次现象的主因**。仍建议后续校正以免在别的模型上产生副作用。
2. **上游 key 映射存疑**：插件把 `qwen3.8-max` / `qmodel_preview` 映射为 `qmodel_38max`，而仓库内 `models_list.json`（上游模型表快照）中 `qmodel_38max` 出现 0 次、真实 key 为 `qmodel_preview`；`KNOWLEDGE.md` §9.4 亦记载「`qwen3.8-max` 当模型 key 服务端不认识」。**但实测 `qmodel_38max` 能正常返回 reasoning 与 tool_calls**，说明该 key 当前有效（`models_list.json` 为 2026-07-26 快照，已过时）。故**不是本次现象的原因**，仅需在下次拉取模型表时复核。
3. **`failed=true` 且 `output_tokens=0` 的 151 条空流**：与本次「有输出但提前结束」是**两类不同故障**，另有 `active ping` 与 `upstream 200: 112` 两条错误线，均不解释本次现象，不在此文档结论内。

## 四、修复方案

**主修复：`tools` 与 agent 上下文按「客户端是否真实声明工具」对齐，禁止无条件套用模板工具集。**

落点：`qoderwork/body.go` + `qoder-ai/body.go` 的 `buildQoderBody`，以及 `openAIRequest` 结构体与解析。

1. `openAIRequest` 增加 `Tools []any \`json:"tools"\`` 与 `ToolChoice any \`json:"tool_choice"\``，让客户端声明的工具不再被静默丢弃。
2. `buildQoderBody` 中按两支处理：
   - **客户端未传 `tools`（当前绝大多数场景）** → `delete(base, "tools")`；若模板含 `tool_choice` 一并删除。同时不再让 agent 上下文误导模型：`agent_id` / `session_type` 需按实测确认是否可改（见下「验证」）。**保留模板 `system prompt`**（`KNOWLEDGE.md` L256 明确「保留它服务器行为才正常」），必要时仅在其尾部追加一条「除非用户在请求中提供了工具，否则直接回答、不要调用工具」的收尾约束。
   - **客户端传了 `tools`** → 用客户端工具**覆盖**模板 `tools`，并透传 `tool_choice`，使真正的 agent 客户端（如 IDE）获得工具回环。
3. 该修复为**从源头消除**：不逐模型特判、不按 `qwen3.8-max` 名字打补丁，而是把「是否具备工具能力」的声明权归还请求方，与 `workbuddy/payload.go:60` 既有的 `normalizeToolsInPlace`（`tool_choice:none` → 删除 tools）语义一致，可复用同一模式。

**实施前必须在生产实测确认的两点**（避免把「修一个缺陷」变成「引入另一个」）：

- 删除 `tools` 后上游是否仍正常返回文本、不报 400/业务错误码（优先用 `qwen-3.8-max` + 各类 prompt 采样）。
- `agent_id` / `session_type` 是否必须保持 `agent_common` / `qodercli`（若改动引发上游拒绝，则本项不动，只删 `tools` + 追加尾部约束）。

**上述两点已用直连上游的隔离实验回答（2026-10-14）**：脚本 `cosy_probe.py` 在服务端复刻 COSY 签名直连 `agent_chat_generation`，用同一长输出 prompt 对比四个变体：

| 变体 | 构造 | toolcall 帧 | finish | content 字符 |
|---|---|---|---|---|
| **V0** | 完全复刻现状（含模板 14 个 tools） | 20 / 30 / 27 | `tool_calls` | 40 / 44 / 33 |
| **V1** | **仅 `delete(base,"tools")`** | **0 ×4** | **`stop`** | **3312 / 4492 / 3964 / 3326** |
| V2 | 删 tools + 追加「禁止调用工具」约束 | 0 | `stop` | 41 帧 |
| V3 | 保留 tools + 追加约束 | 0 | `stop` | 194 帧 |

**结论：仅删除 `tools` 数组即足够**（V1 四次采样全部 `toolcall=0`、`finish=stop`、正文 3300~4500 字符），**无需改动 system prompt**（`KNOWLEDGE.md` L256 要求保留它），也**无需改动 `agent_id` / `session_type`**。故最终实现只做「工具集按客户端声明对齐」一件事，不引入额外约束文本、不触碰 agent 上下文。

## 六、结论

- **不是 `qwen-3.8-max` 模型的问题**：同一模型、同一 prompt，非流式返回完整 20908 字节正文、`finish=stop`；注入「禁止调用工具」约束后流式同样输出 7485 字符完整正文、`tool_calls` 归零。
- 根因是 **qoder 系插件的 `baseprompt.json` 无条件注入 Qoder CLI 的 14 个 agent 工具 + agent 会话上下文 + 「主动用工具/引用给 file:line」的 system prompt，而 `buildQoderBody` 对 `tools` 零处理、`openAIRequest` 又丢弃客户端工具**，导致上游把普通问答当 agent 任务作答，以 `finish_reason=tool_calls` 提前结束；下游无工具回路，用户看到「推理一小段就停」。
- 「其他模型不会这样」的原因：`glm-5.3` 等由 **traework 插件**承载，不经过 `baseprompt.json`。
