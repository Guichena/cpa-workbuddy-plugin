# 成长中心能量余额误计入收益与宿主引号键致配置静默失效根因诊断与修复

- Bug 编号：BUG-GROWTH-ENERGY-BALANCE-AND-QUOTED-KEYS-20261016
- 发现时间：2026-10-16 00:30（北京时间，用户面板实测「点了成长中心没有积分增加，但有提示能量增加」）
- 影响范围：workbuddy-provider 0.16.x 的成长中心面板摘要显示（能量误导）+ 全部经宿主持久化的插件配置键解析（`checkin_auto` / `growth_auto` / `lifecycle_auto` / `scheduler_mode` / `management_key` / `usage_report_*` 等）
- 严重级别：中（能量显示误导用户；引号键使部分开关静默失效，直接影响「用配置关闭功能」的能力）
- 状态：**已定位 / 已修复（0.16.2）**

## 1. 现象

用户在管理面板对 CN 账号点击「成长中心」按钮后：

1. 卡片摘要行显示「+0 积分 / +8 能量 / 0 任务」——**积分没有增加，但提示能量增加**；
2. 对同一账号连续点击，摘要行每次都报「+N 能量」（N 等于该账号当前能量余额，如 3、8、13），即使该轮**没有任何领取动作**。

## 2. 根因

### 2.1 直接原因：能量余额被累加进「本轮收益」

`workbuddy/growth.go` 的 `runGrowthForAccount` 汇总段把 `/energy` 端点的 `balance`（账号能量**余额快照**）累加进了 `EnergyGained`（**本轮收益**）：

```go
// 8. 汇总：能量余额与连登天数只读读取
if m, err := fetchGrowthEnergy(sa); err == nil {
    res.EnergyGained += jsonI64(m, "balance")   // ← 余额 ≠ 收益
}
```

面板读取 `energy_gained` 并渲染为 `+N 能量`，于是余额被显示成收益。

**生产实测证据**：对生产账号 `5839bac3d81dc916` 连续执行两次单账号 `POST /growth`：

| 轮次 | segments | energy_gained |
| --- | --- | --- |
| 第 1 次 | `["buddy_open","streak=0"]` | 3 |
| 第 2 次 | `["streak=0"]`（**零领取动作**） | 3（仍报） |

第 2 次没有任何写操作，`energy_gained` 仍等于账号能量余额 3——即余额污染的直接证据。

**契约对照**：外部项目 EXT-1（`88lin/workbuddy-auto-signin` 的 `signin.py`）在第 7 段明确注释「能量 & 连签状态（**纯展示值**，预算不够就直接不取，不计失败）」，其报告格式为「能量 42」（不带 `+`），与收益字段（`credits_gained` 累计）完全分离。插件转写时把「读取余额」与「累加收益」错误地合并。

### 2.2 为什么单测没拦住

原有测试只断言 `CreditsGained` 与 `TasksAccepted/TasksClaimed`，**从未断言 `EnergyGained`**；桩响应里 `/energy` 返回 `{"balance":42}`，即使被累加进收益也无人察觉（`grep EnergyGained workbuddy/*_test.go` 零命中）。

### 2.3 同族隐患（本轮一并修复）：宿主引号键致配置静默失效

调查过程中发现更深的隐患：**宿主持久化会保留 YAML 键的引号样式**。

- 生产 spool `config.yaml` 中 `workbuddy-provider` 节实际形态：
  ```yaml
  workbuddy-provider:
    "enabled": true
    "lifecycle_auto": false
    "models": []
  ```
- 宿主把该配置下发给插件时**原样保留引号**（本地实验确证：`yaml.Unmarshal` → `yaml.Marshal` 保留 `Style`，输出仍为 `"growth_auto": false`）；
- 而插件解析器用裸前缀匹配（`strings.HasPrefix(line, "growth_auto:")`），**带引号的键行会被整行忽略**。

后果：只要配置经过宿主持久化（PUT/PATCH/plugin-store install 任一写回），用户写的 `"lifecycle_auto": true` 等开关就会静默失效——这是「配置写了但不生效」类问题的根因，也直接威胁 0.16.2「默认开启 + 可用 `growth_auto: false` 关闭」的交付正确性。

## 3. 修复

### 3.1 能量余额与收益字段分离（0.16.2）

```go
type growthResult struct {
    CreditsGained int64 `json:"credits_gained"`
    EnergyGained  int64 `json:"energy_gained"`   // 只统计各段实发值
    EnergyBalance int64 `json:"energy_balance"`  // 余额快照，独立字段
    ...
}

// 8. 汇总：余额是快照，记入 EnergyBalance 而非收益
if m, err := fetchGrowthEnergy(sa); err == nil {
    res.EnergyBalance = jsonI64(m, "balance")
}
```

面板同步（`panel.html`）：`+N 积分 / +M 能量 / K 任务（能量余额 B）`，余额单独展示、不加 `+` 号；无收益时仍显示「今日已领完」。

### 3.2 引号键归一化（0.16.2）

新增 `normalizeConfigKeyLine`，在解析前剥离键名两端引号（仅处理冒号前的键名，值部分原样保留）：

```go
func normalizeConfigKeyLine(line string) string {
    if !strings.HasPrefix(line, "\"") && !strings.HasPrefix(line, "'") {
        return line
    }
    q := line[0]
    end := strings.IndexByte(line[1:], q)
    if end < 0 {
        return line
    }
    end++
    rest := line[end+1:]
    if !strings.HasPrefix(rest, ":") {
        return line
    }
    return line[1:end] + rest
}
```

覆盖点：`usage_config.go` 的全部开关解析（`checkin_auto` / `growth_auto` / `lifecycle_auto` / `account_failover` / `scheduler_mode` / `usage_report_*` / `management_key` / `token_keepalive` / `min_routable_credits` / `retry_on_4xx`）与 `usage_feed.go` 的 feed 配置。

### 3.3 growth_auto 默认开启（0.16.2）

用户明确要求「成长中心要自动开启」。按「生产变更走插件更新链路」的边界，默认值在代码内改为 `true`（`growthAuto = true`、`nextGrowthAuto := true`），随 0.16.2 插件更新交付；用户可用 `growth_auto: false` 显式关闭。此前通过管理 API PATCH 写入的 `growth_auto` 键已删除（PATCH null），生产配置恢复原状。

## 5. 教训

1. **「余额」与「收益」是两种语义，字段必须分离**：读取快照值与累加收益值混用一个字段，会让零操作轮次也显示收益。凡是「读取当前值 + 累计增量」并存的功能，必须用两个字段承载。
2. **外部项目的动态类型契约转写到强类型语言时，要逐个字段核对消费方式**：EXT-1 用 `dig()` 原样取值，Python 不会暴露「余额被当收益」的语义错误；转写时必须回到「该值被怎么用」而不是「该值长什么样」。
3. **配置解析必须容忍宿主序列化形态**：YAML 键的引号样式会经宿主持久化保留并透传，裸前缀匹配在真实链路上不可靠；解析前先做键名归一化。
4. **测试断言要覆盖全部对外契约字段**：`energy_gained` 从未被断言，缺陷潜伏至今；本轮已补全（全绿路径 + 零领取路径 + 引号键形态）。
