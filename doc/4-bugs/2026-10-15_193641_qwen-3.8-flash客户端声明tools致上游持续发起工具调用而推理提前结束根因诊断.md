## 三、根因

### 3.1 触发层：模板 agent 上下文使每次问答都进入 agent 模式

`qoderwork/baseprompt.json`（`qoder-ai/baseprompt.json` 逐行同构）自带 agent 会话上下文与 14 个工具：

```json
{
  "agent_id": "agent_common",
  "session_type": "qodercli",
  "chat_task": "FREE_INPUT",
  "tools": ["Bash","BashOutput","Edit","Glob","Grep","ImageGen","KillBash",
            "Read","Skill","Task","TodoWrite","WebFetch","WebSearch","Write"],
  "messages": [
    {"role":"system","content":"<12324 字符 Qoder CLI system prompt>"},
    {"role":"user","content":"","contents":[{"type":"text","text":"<system-reminder>…<available_skills>…"}]}
  ]
}
```

`buildQoderBody`（[body.go:245-332](file:///F:/cpa-plugin/qoderwork/body.go#L245)）把客户端消息拼进 `messages`，但**模板的 system prompt 与 `<system-reminder>` / `<available_skills>` 段始终保留**，且 `agent_id` / `session_type` / `chat_task` 不变。上游因此把每次问答都当 agent 任务。

`alignToolsWithClient`（[body.go:138-157](file:///F:/cpa-plugin/qoderwork/body.go#L138)）在 0.9.36 已修复「客户端**未**声明工具 → 剥离模板 14 工具」，但按设计**客户端声明了就原样透传** —— Qoder Desktop 本来就声明 tools（Read/Bash/Edit/Glob…），于是走上「透传 → 上游发起工具调用」分支。

### 3.2 断链层：插件重建 messages 时丢弃工具结构

```go
// qoderwork/body.go:64-67
type openAIMessage struct {
	Role    string `json:"role"`
	Content string `json:"content"`
}
```

```go
// qoderwork/body.go:311-316 —— 重建时只搬 role + content
for _, m := range req.Messages {
	systemMsgs = append(systemMsgs, map[string]any{
		"role":    m.Role,
		"content": m.Content,
	})
}
```

后果：客户端多轮历史里的

- `assistant.tool_calls`（工具调用及其 `id`）→ **被丢弃**，只剩 `content`（通常为空串）；
- `role:"tool"` 消息的 `tool_call_id` → **被丢弃**，`content`（工具结果）以**孤立 user/tool 文本**形式留在历史中。

上游看到的历史因此是「assistant 说了空话 → 某条无主的结果文本 → 继续」，**无法把工具结果与先前的工具调用配对**，于是重复发起同类工具调用。

**判据**：`/v1/chat/completions` 路径下，把工具结果**结构化回传**（`assistant.tool_calls` + `role:"tool"` + `tool_call_id`）时模型仍不收敛，而把同一结果**改写为纯 user 文本并附「直接给最终答案、不要再调用工具」**时**立即收敛**（正文 481 字符、`finish=stop`、`tool_calls` 空）——证明配对信息的缺失直接影响收尾判定。

### 3.3 放大层：模板 system prompt 的「主动用工具」约束

模板 system prompt（12324 字符）含 `# Tool usage policy`（主动用工具）与 `# Code References`（引用必须给 `file:line`）。这两条使模型在**探索型任务**（「找出所有 X」「分析这个项目」）下持续发起工具调用，即使在无工具声明时也会退化为**文本式 `<tool_call>`**（见 2.3 的 C1）。

### 3.4 根因分层（主因 / 放大器，边界已实测）

**主因（决定症状出现）：上游模板的 agent 会话上下文使每次问答都进入 agent 模式。**
`baseprompt.json` 的 `agent_id=agent_common` / `session_type=qodercli` / `chat_task=FREE_INPUT` + 12324 字符 system prompt（含 `# Tool usage policy`、`# Code References` 必须给 `file:line`）无条件上行。2.3 的 C1 是直接证据：**即便客户端完全不声明 tools**，`qwen-3.8-flash` 在编程任务下仍把工具调用**写成正文文本**（`<tool_call><function=Glob>...`）—— 说明 agentic 倾向来自模板上下文，`tools` 数组只是它的一个出口。

**放大器（决定症状严重度）：插件重建 `messages` 时丢弃 `assistant.tool_calls` 与 `tool.tool_call_id`**（[body.go:64-67](file:///F:/cpa-plugin/qoderwork/body.go#L64)、[body.go:311-316](file:///F:/cpa-plugin/qoderwork/body.go#L311)）。多轮 agent 往返中，工具结果因此失去与工具调用的配对关系，模型更难判定「该探测的都探测完了」，倾向于重复发起同类调用。

**边界（必须诚实标注）**：2.5 的两组对照显示，**保留结构本身不是充分条件**——
- 探索型任务 + 2 轮固定历史：MALFORMED 8/8 不收敛、FULL **同样 8/8 不收敛**；
- 单次工具即可解决的任务：MALFORMED 6/6 收敛、FULL 同样 6/6 收敛。

⇒ 在探索型任务下，**「历史配对是否完整」不足以单独决定收敛**；模型是否会收尾更多取决于任务本身的探索深度与模板 system prompt 的强制程度。修复必须同时处理「配对完整性」（方案 A）与「探索倾向抑制」（方案 B），单做 A 预期只能部分缓解。

**另一条独立线索（未验证）**：`buildQoderBody` 把 `chat_context.text` 设为 `extractLatestUserPrompt(req.Messages)`（[body.go:251](file:///F:/cpa-plugin/qoderwork/body.go#L251)），在 agent loop 中客户端只追加 `role:tool`/`role:assistant`、不新增 user 消息，该函数会**始终回退到最初那条用户提问**。若上游以 `chat_context.text` 为当前轮实际输入，则模型每轮都看到同一个原始问题、每轮都从头探测——这会是比「配对缺失」更直接的解释，但**本轮未经上游直连验证**（全部实验经 CPA 转译），列为待查项。

## 五、修复方案

### 方案 A（推荐，治本）—— 重建 messages 时保留工具结构

**落点**：`qoderwork/body.go` 与 `qoder-ai/body.go`（逐行同构同步）。

**改动**：

1. `openAIMessage` 补 `ToolCalls`（`json:"tool_calls"`）与 `ToolCallID`（`json:"tool_call_id"`）字段，并透传 `name`（`role:"tool"` 消息可选）。
2. `buildQoderBody` 重建 messages 时，**凡非空字段一律保留**，不再只搬 `role`/`content`。

**判据**：修复后，客户端多轮历史里的工具调用与结果能正确配对，模型在探索型任务下的重复工具调用应显著减少、正文不再恒为 0。

**风险**：上游 `agent_chat_generation` 对 `messages` 的接受形态**未经直连实测**（本轮全部经 CPA 转译）。若上游只认文本 content，则需把结构化历史**降级为带配对标识的文本**（如 `[tool_call id=c1 name=Glob args=...]` / `[tool_result id=c1] ...`），确保配对信息不丢。**这一形态必须先在测试环境验证。**

### 方案 B（配套，缓解）—— 抑制探索型任务的工具倾向

若方案 A 后仍有残留，可在模板 system prompt 尾部追加一条收尾约束（类似 2026-10-14 已验证有效的「禁止调用工具」实验）：仅在客户端**未声明**工具时追加；声明了则不动（真正的 agent 客户端需要工具）。

**依据**：2026-10-14 实测「追加禁止约束 → `tool_calls` 归零、正文 7485 字符」，是本仓库已验证有效的抑制手段。

### 方案 C（**已作废**）—— 下调 `max_tokens`

本轮证据显示低正文样本 `out` 仅数百量级，**与 max_tokens 截断无关**；且 `2026-10-15_171500_*` 已实测证明 `max_tokens` 双向皆害。不作候选。

## 八、诊断过程中排除的假设

| 假设 | 排除依据 |
|---|---|
| 账号问题 | 低正文记录分散在 8 个不同 `auth_index`（2.2） |
| `max_tokens` 截断 | 低正文样本 `out` 仅 24–90，远未触及 32768 上限（2.2） |
| 排队帧 / 上游容量 | 该时段无 `isQueued` 帧；`serviceAvailable` 未出现（CPA 日志全量） |
