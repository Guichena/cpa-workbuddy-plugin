# Qoder 排队帧被误判为账号级故障且跨 provider 状态码通道缺失根因诊断

- 编号：BUG-QODER-QUEUE-FRAME-CLASSIFY-20261015
- 发现时间：2026-10-15（用户报告"排队好像很重要，我们上次另一个插件好像也有排队的问题，我们这次一起解决吧"）
- 判定时间：2026-10-15 16:00（北京时间）
- 状态：**已定位，修复实施中**（qoderwork-provider / qoder-ai-provider 双插件同步；宿主侧异步流通道另立改动计划）
- 关联历史：`doc/4-bugs/2026-10-12_001641_Qoder上游200排队帧未被识别致new-api调用qwen3.8挂死根因诊断.md`（上一轮修复：识别排队帧，消除 60s 挂死）、`doc/5-tests/2026-10-11_164802_Qoder排队帧识别回归.md`

## 1. 现象

从 new-api 请求 CPA 的 `qwen-3.8-flash`（qoderwork-provider 承载）持续失败，报错原文：

```
HTTP 503
{"error":{"message":"auth_unavailable: no auth available
  (providers=qoderwork-provider, model=qwen-3.8-flash;
   last upstream error: upstream 200: 403: 10605:
   {\"isQueued\":true,\"modelKey\":\"qfmodel\",\"queueCount\":14250,
    \"queueType\":\"p3\",\"retryAfterSeconds\":30,
    \"serviceAvailable\":true,\"waitTime\":478})",
 "type":"server_error","code":"internal_server_error"}}
```

即：**上游明确返回 `serviceAvailable:true`（服务可用，只是在排队），但 CPA 侧最终报出 `no auth available`——整池账号都不可用了。**

## 2. 复现路径与环境

- 环境：生产 CPA（容器 `cli-proxy-api`），qoderwork-provider / qoder-ai-provider 当前版本。
- 链路：客户端 → new-api → CPA → qoderwork-provider → 阿里 Qoder 上游。
- 触发条件：上游进入排队窗口（`isQueued:true`，`queueCount` 上万，`waitTime` 数百秒），向该 provider 发任意请求即可。
- 稳定性：**稳定复现**。CPA 容器日志显示 6 个 qoderwork 账号**依次**命中同一排队，`queueCount` 从 14176 → 14198 → 14209 → 14222 → 14250 单调递增，`waitTime` 稳定在 476–478 秒。

## 3. 根因

**两个独立缺陷叠加**，均在插件侧（宿主只读，见 §5.3）：

### 3.1 缺陷一：排队帧被当成账号级故障，给健康账号打冷却

排队帧识别本身已在上一轮修好（`parseQoderSSEChunk` 第 4 类形态、`sseErrorFrame` 顶层 code 提取、`unwrapNestedMessage` 逐层展开）。**但识别之后的记账语义是错的**：

`qoderwork/stream.go:334`（qoder-ai 同构同位置）：
```go
noteAccountFailure(curAuthID, http.StatusForbidden, sseErr)
```

把排队错误**硬编码 remap 成 403**，而 403 命中 `accountFailover.go:128` 的 `isAccountLevel4xx` → 走**硬失败**通道 → `count++` + **15 秒冷却**。非流式路径同款处理（`qoderwork/main.go:825-829`）。

**这与上一轮 Bug 单 §6 的结论直接矛盾**。该节已明确认定：

> 排队是「请求级 + 时段性」，不是账号级。同账号 ok/bad 混合……换号不一定救回。

既然已认定非账号级，就**没有任何依据**把账号记一次故障并冷却 15 秒。后果是：上游一进入排队窗口，每个被路由到的健康账号都被逐个打进冷却，15 秒 × 6 账号 ≈ 90 秒内整池全冷 → 宿主报 `no auth available`——这正是 §1 现象的直接成因。

注意区分两个不同问题：
- **同请求内不换号是对的**（`TestQueueFrameDoesNotRotate` 锁定）：同一时刻多个账号会被同时排队，号池内换号纯属浪费。
- **跨请求把账号打进冷却是错的**：账号健康度与上游队列状态无关，冷却它只会把容量问题放大成"整池不可用"。

### 3.2 缺陷二：跨 provider 状态码通道缺失，逃生口从未接上

上一轮 §6 推论："要真正提升成功率，需要另做排队帧出现时的**跨 provider 换道**"。宿主**确实支持**同模型多 provider 轮转，但有闸门：

1. `sdk/cliproxy/auth/conductor_cooldown.go:1448` `statusCodeFromError` **只认 `StatusCode() int` 接口**，拿不到就返回 `0`；
2. `sdk/cliproxy/auth/conductor_selection.go:1452` `isCredentialRetryRoundStatus` 白名单为 **403 / 408 / 429 / 500 / 502 / 503 / 504**；
3. 而本仓库所有 provider 插件的 `envelopeError` 只有 `Code` + `Message` 两个字段（`qoderwork/main.go:314`），**没有一个携带 `http_status`** → 宿主 `statusCodeFromError` 恒得 `0` → 白名单永不命中 → **跨 provider 轮转从未被触发**。

宿主 ABI 是支持的：`sdk/pluginabi/types.go:121-128` 的 `Error.HTTPStatus`，且同仓 `cursor` 插件已经这么用（`cursor/internal/plugin/types.go:42`），可作参考样例。

**可用逃生口现状**：`qwen-3.8-flash` 同时被 qoderwork-provider 与 traework-provider 认领，`qwen-3.8` 被 qoder-ai-provider 认领。排队是 **Qoder 上游的容量问题**，而 traework 是**另一家上游**（Trae）——跨过去正是有效逃生。

### 3.3 两缺陷的相互作用

缺陷一让健康账号被逐个冷却，缺陷二让请求无法跨到另一家上游。两者叠加的效果是：**上游排队 → 插件把自家账号全冷掉 → 宿主无处可去 → 客户端收到 `no auth available`**，把上游的"暂时排队"放大成了 CPA 侧的"完全不可用"。

## 4. 证据

- **生产报错原文**（§1）：`last upstream error` 明确含 `serviceAvailable:true` + `queueCount:14250`，而外层是 `auth_unavailable: no auth available`。
- **CPA 容器日志**：6 个 qoderwork 账号依次命中同一排队，`queueCount` 14176→14198→14209→14222→14250 单调递增、`waitTime` 476–478s——证明是**同一上游队列**被多个账号分别撞上，非账号级。
- **代码事实**：
  - `grep -rn "http_status\|HTTPStatus" qoderwork/ qoder-ai/ workbuddy/ workbuddy-ai/ traework/ zcode/` = **0 命中**（全部插件均不携带状态码）。
  - `qoderwork/stream.go:334` / `qoder-ai/stream.go:334` 硬编码 `noteAccountFailure(curAuthID, http.StatusForbidden, sseErr)`。
  - `qoderwork/main.go:828` / `qoder-ai/main.go` 非流式同款 remap。
- **宿主事实**（只读核实，`F:/CLIProxyAPI`，独立仓库）：
  - `conductor_cooldown.go:856-862`：宿主 `MarkResult` 对 403 给凭据打 **30 分钟冷却**；`conductor_cooldown.go:949` 对 503 只打**瞬时冷却（默认 1 分钟，`transientErrorCooldown = time.Minute`）**。二者都在轮转白名单内。
  - `internal/pluginhost/stream_bridge.go:46-55`：`host.stream.close` 只读 `stream_id` + `error` 两个字段；`host_callbacks.go:386-389` 把 `error` 包成 `fmt.Errorf("%s", req.Error)`——**纯文本，无结构**。
  - `internal/pluginhost/rpc_client.go:360-374`：非流式失败信封经 `decodeEnvelopeResult` 读 `Error.HTTPStatus` → 可带数字状态码。

## 5. 修复方案

### 5.1 第 1 步：排队帧不再误判为账号级故障

新增判别函数（放 `policy.go`，与既有 marker 体系同层），命中排队/容量语义时**不进硬失败通道**：

- 命中时只做**软记账**（`coolDownAccount`，仅 15s 冷却、不推进 `count`），或**完全不记账**（排队是纯上游容量状态，与账号无关）。
- 依据：既有 `isTransientThrottle` 已经是"瞬时过载不计数"的成熟机制，排队帧属于同一类语义。

**落点**（qoderwork / qoder-ai 逐处同构）：
- `stream.go` pump 路径 `sseErr` 分支（`:334`）
- `stream.go` collect 路径 `sseErrMsg` 分支（`:491` 附近）
- `main.go` 非流式 remap 分支（`:825-829`）

### 5.2 第 2 步：状态码通道打通跨 provider 轮转

给 `envelopeError` 补 `HTTPStatus` 字段（对齐 `pluginabi.Error.HTTPStatus` 与 cursor 样例），排队帧错误带上**数字状态码**，使宿主 `statusCodeFromError` 命中白名单从而跨 provider 轮转。

**状态码选型（本轮核实后修正）**：选 **503** 而非 403。理由：
- 403 会让宿主给凭据打 **30 分钟冷却**（`conductor_cooldown.go:856`），与第 1 步"不给账号冷却"直接冲突，且排队是分钟级现象，30 分钟冷却严重过度。
- 503 只触发**瞬时冷却（默认 1 分钟）**（`conductor_cooldown.go:949`），与排队的时间尺度吻合，且 `serviceAvailable:true` 语义上就是"服务暂时不可用、稍后重试"。
- 503 同样在宿主轮转白名单（`isCredentialRetryRoundStatus`）内，跨 provider 换道照样触发。

### 5.3 宿主侧异步流通道（另立计划，不在本仓库实施）

生产流式请求走**异步路径**（插件 `streamEmitError` → `host.stream.emit` 的 `error` 字段），该通道**只有字符串、无结构**，插件侧无论怎么改都带不上状态码。需宿主侧 `stream_bridge.go` 读取结构化错误详情。

**CLIProxyAPI 是独立仓库**（`F:/CLIProxyAPI/.git`，remote `luode0320/CLIProxyAPI`），按本仓库跨项目红线**只读，不在本会话修改**。产出改动计划文档，交用户在该项目另开会话执行。

## 6. 未覆盖与后续风险

- **未覆盖**：`retryAfterSeconds:30` 的排队语义下，上游是否期望客户端等待后重试。本轮不实施短退避重试——今日实测 `waitTime:478`、`queueCount:14250`，此深度下等 30 秒仍在排队，等待只会占住连接；把"要不要等"交给第 2 步的跨 provider 换道。
- **未覆盖**：`traework` / `workbuddy` / `zcode` 的上游协议不同（Trae 是 `event:error` 帧、zcode 是 Anthropic 形态），**无同形排队帧**，本轮不同步；`workbuddy` 系 `sseErrorFrame`（`workbuddy/stream.go:738`）不认顶层 `code`，但其上游不发该形态，属"不同协议不做同形假设"。
- **风险**：第 2 步改变了排队错误的对外状态码（200 → 503），会影响 new-api 侧的日志与计费判读（当前记"上游没有返回计费信息"）。需在发布验收时确认行为符合预期。
- **风险**：修复涉及 `stream.go` / `main.go` / `policy.go` 的公共记账路径，属高影响面改动，须走完整回归（cgo-shim build/vet/test + 6-review + 生产热重载验收）。

## 7. 结论

`qwen-3.8-flash` 报 `no auth available` 不是账号真的不可用，而是**插件把上游的排队状态误当成账号故障，逐个冷掉了自己的健康号池**；同时因为错误只带纯文本、不带数字状态码，宿主那层"跨 provider 换道"的逃生口从未被触发。

修复分两步：① 排队帧不再进账号级记账（止血，消除"整池不可用"）；② 排队错误带上 503 状态码，打通宿主跨 provider 轮转（把请求送到另一家上游）。异步流式路径的状态码透传需宿主侧配合，另立计划。
