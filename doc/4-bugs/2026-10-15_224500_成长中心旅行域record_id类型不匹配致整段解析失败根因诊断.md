# 成长中心 Buddy 旅行域 record_id 类型不匹配致整段解析失败根因诊断与修复

- Bug 编号：BUG-GROWTH-TRAVEL-RECORDID-TYPE-20261015
- 发现时间：2026-10-15 22:17（北京时间，0.16.0 生产部署后首次行为验收）
- 影响范围：workbuddy-provider 0.16.0 的 Buddy 旅行段（`/buddy/travel/status` → claim → config → depart 全链路）
- 严重级别：中高（7 类玩法中的旅行段对全部 CN 账号完全失效；其余 6 段正常）
- 状态：**已定位 / 已修复（0.16.1）**

## 1. 现象

0.16.0 通过 `plugin-store install` 热重载到生产后（`active_version=0.16.0 retired_version=0.15.10`），对生产真实入口执行 `POST /v0/management/plugins/workbuddy-provider/growth`（空 body = 全量 CN 扇出），**10/10 账号**返回 `success: false`，每条都携带同一条错误：

```
travel_status: json: cannot unmarshal number into Go struct field growthTravelStatus.record_id of type string
```

分段结果佐证：`segments` 里只有 `streak=N` 与少量 `tasks_accept` / `buddy_open`，**没有任何 `travel_claim` / `travel_depart`**——旅行段的收礼与派出两个写操作一次都没发出。

## 2. 根因

### 2.1 直接原因：强类型 string 绑定与上游 number 形态冲突

`workbuddy/growth.go` 的 `growthTravelStatus.RecordID` 声明为 `string`：

```go
type growthTravelStatus struct {
    State             string `json:"state"`
    RecordID          string `json:"record_id"`   // ← 上游实际返回 number
    ...
}
```

而上游 `/v2/activity/growth/buddy/travel/status` 的 `record_id` 实际是 **JSON number**（如 `9001`）。`json.Unmarshal` 遇到 number → string 的类型冲突直接返回错误，`fetchTravelStatus` 把整个 envelope 解析失败向上抛，`growthRunTravel` 第一步即 `return`，后续 claim / config / depart 全部不执行。

### 2.2 为什么单测没拦住

测试桩按「字符串形态」构造响应（`"record_id":"r-1"`），与生产真实形态（`"record_id":9001`）不一致。契约来源 EXT-1（`88lin/workbuddy-auto-signin` 的 `signin.py`）用的是 `dig(sbody, "record_id")` 原样取值、不做类型断言，Python 动态类型天然不会暴露该差异；Go 侧转写时按「ID 应该是字符串」的直觉做了强类型绑定，而测试桩又沿用了同一直觉。

### 2.3 同族隐患：另外两个字段同样绑定错误

`ArriveAt string` / `ServerNow string` 也是同类问题——EXT-1 的 `_fmt_eta(arrive_at, server_now)` 明确按 `float()` 数值时间戳消费（`float(arrive_at) - float(server_now)`），说明上游同样是 number。这两个字段在插件侧**从未被任何代码读取**，本次一并删除，避免日后启用时再次踩雷。

`growthTravelLocation.ID` 存在相同风险面：config 返回的 `id` 与 depart 请求的 `location_id` 是同一族 ID，形态未证实为字符串，一并改为原样透传。

## 3. 修复

### 3.1 改为 json.RawMessage 原样透传（0.16.1）

```go
type growthTravelStatus struct {
    State             string          `json:"state"`
    RecordID          json.RawMessage `json:"record_id"`
    DailyLimitReached bool            `json:"daily_limit_reached"`
}

type growthTravelLocation struct {
    ID            json.RawMessage `json:"id"`
    Name          string          `json:"name"`
    DurationHours int64           `json:"duration_hours"`
}
```

`claimTravelReward` / `departBuddy` 签名同步改为 `json.RawMessage`，写请求 body 内**原样回传**：数字形态保持数字、字符串形态保持字符串。这样同时避免了大整数经 `float64` 中转丢精度（Go 的 `any` 解码默认走 float64，超过 2^53 会失真）。

### 3.2 新增判空辅助 growthIDEmpty

```go
func growthIDEmpty(raw json.RawMessage) bool
```

字段缺失 / `null` / 空串 / 纯空白串一律在发请求前拦截，杜绝用无效 ID 打写端点（保持原有「空 ID 不发请求」语义）。

### 3.3 回归用例按上游真实形态重写

- `TestFetchTravelStatus_ParsesThreeStates`：`record_id` 同时覆盖 number（`9001`）与 string（`"r-1"`）两种形态。
- `TestClaimTravelReward_SendsRecordID`：断言 body 内 `record_id == float64(9001)`（即仍为数字），而非被强转成字符串。
- `TestTravelWriteEndpoints_RejectEmptyIDs`：覆盖 `nil` / `null` / `""` / `"  "` 四种空值形态。
- 全部测试桩的 travel_status 响应改为上游真实形态（number + 数值时间戳）。

**变异自测**：临时把 `claimTravelReward` 的 body 值改为 `string(recordID)`，`TestClaimTravelReward_SendsRecordID` 立即 FAIL（`body=map[record_id:9001]`）；回滚后全绿。证明新断言确实能捕获类型转换退化。

## 5. 教训

1. **行为验收不可省**：本次缺陷在 build / vet / 全部单测（45 例成长中心用例）下都是全绿，只有对生产真实入口发一次请求才暴露。契约来自「外部项目转写」而非真实响应时，类型形态必须用真实数据校准。
2. **外部项目是 Python 时，动态类型会掩盖契约细节**：`dig()` 取值不断言类型，转写成 Go 强类型必须逐个字段确认真实 JSON 类型，不能按语义直觉（「ID 应该是字符串」）绑定。
3. **测试桩必须对齐生产真实形态**：桩按直觉构造会形成「测试通过但线上必挂」的假绿。发现线上形态与桩不一致时，第一动作是把桩改成真实形态并让用例失败，再修实现。
