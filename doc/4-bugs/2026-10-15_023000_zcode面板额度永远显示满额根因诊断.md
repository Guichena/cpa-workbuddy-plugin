# zcode-provider 面板额度永远显示满额根因诊断

## 一、问题描述

- **现象**：生产多个 zcode 账号的每日额度已被真实消耗，但面板卡片始终显示「GLM-5.3 3.00M / daily · GLM-5.3-Flash 5.00M / daily 合计 8.00M」，绿色进度条**恒为 100% 满格**，从不随用量变化。用户报「生产的一些账号的额度可能已经使用了，但是面板额度从来没有刷新，额度好像一直保存最满的状态」。
- **发现方式**：2026-10-15 用户反馈（附面板截图）。
- **结论（本诊断）**：**额度数据源选错 + 面板渲染硬编码**双重缺陷。
  1. 插件 `fetchAccountQuota` 取数走 `GET /api/v1/zcode-plan/billing/current`，该端点**只返回授予量 `grant_units`，不含任何已用/剩余字段**——用授予量充当「额度」，自然恒满。
  2. 面板 `quotaHTML` 无条件渲染 `width:100%`，即使有真实用量也不会体现。
  真实用量在 `GET /api/v1/zcode-plan/billing/balance?app_version=<v>`，此前被误判为「免费账号不可用」而弃用。

## 二、证据链（生产真实账号实测 + app.asar 逆向）

### 2.1 billing/current 不含任何用量字段（生产实测）

对生产 7 个 zcode 账号逐一请求 `GET /api/v1/zcode-plan/billing/current`，仅返回 `data.plans[].entitlements[]`：

```json
{"entitlement_id":"ent_2_0817_glm_5p3","show_name":"GLM-5.3",
 "grant_units":3000000,"period":"daily","meter":"model_usage"}
```

字段清单：`entitlement_id` / `show_name` / `meter` / `unit_type` / `capabilities` / `grant_units` / `period` / `priority` / `effective_at`——**无 `used_units` / `remaining_units` / `total_units`**。授予量恒为 3,000,000 / 5,000,000，与消耗无关。

### 2.2 billing/balance 才含真实用量（生产实测）

同一账号请求 `GET /api/v1/zcode-plan/billing/balance?app_version=unknown`，返回 `data.balances[]`：

```json
{"entitlement_id":"ent_2_0817_glm_5p3","show_name":"GLM-5.3",
 "total_units":3000000,"used_units":19,"remaining_units":2999981,
 "available_units":2999981,"period_start":1791993600,"period_end":1792079999}
```

**决定性对照**（账号 `zcode-d7a0cb4afa8f77c0`）：`used_units=19` 非 0，而 current 端点对同一账号只给 `grant_units=3000000`。生产全量实测：

| 账号 | 授予 | 已用 | 剩余 | 剩余占比 |
| --- | --- | --- | --- | --- |
| ZCode upjrjje0 | 8,000,000 | **255,381** | 7,744,619 | **96.8%** |
| ZCode de luo | 8,000,000 | 16 | 7,999,984 | 100.0% |
| ZCode 旅行者1463 | 8,000,000 | 19 | 7,999,981 | 100.0% |
| ZCode 欧皇小德子 | 8,000,000 | 0 | 8,000,000 | 100.0% |

`ZCode upjrjje0` 已用 25.5 万 token，旧面板却显示为满格——直接印证缺陷。

### 2.3 balance 端点「此前不可用」的真因：缺设备三头

早期记录称「balance 对免费 start-plan 账号固定返回 `400 code 3001 parameter error`」，故弃用。2026-10-15 参数扫描定位真因：**缺 `X-Platform` / `X-Device-Mid` / `X-ZCode-App-Version` 三个设备头**（或缺 `app_version` 查询参数）即 3001；三者齐备后稳定 200。

| 请求条件 | 结果 |
| --- | --- |
| 仅 `Authorization` + `app_version` | `400 code 3001 parameter error` |
| `+ X-Platform` + `X-Device-Mid` + `X-ZCode-App-Version` | **`200 code 0` + 完整 balances** |
| `X-ZCode-App-Version: unknown`（插件默认放行值） | 200（与 3.15.1 同） |

### 2.4 app.asar 逆向佐证（客户端同一通道）

ZCode 3.15.1 `app.asar`：

- `buildZCodeEndpointUrls` 定义 `zcodePlanBillingBalanceUrl = ${origin}/api/v1/zcode-plan/billing/balance`。
- `buildZaiStartPlanBalanceUrl`（`function ia`）：`new URL(Lhe); searchParams.set("app_version", En)`——即 balance 端点带 `app_version`。
- `fetchZaiStartPlanBalanceEnvelope`（`function Qw`）：以 `Authorization: <token>` GET 该 URL，响应经 `normalizeStartPlanExpiry`。
- `normalizeZaiStartPlanBalanceLimits`（`function Q1`）消费 `total_units` / `used_units` / `remaining_units`；`buildZaiStartPlanRemaining`（`function rve`）以 `remaining/number` 计算百分比驱动额度条。

即：**桌面客户端额度条本来就读取 balance 端点的真实用量**，插件此前读 current 是数据源选错。

## 三、根因

| 层 | 缺陷 | 位置 |
| --- | --- | --- |
| 取数 | 读 `billing/current`（仅授予量），未读 `billing/balance`（含真实用量）；误判 balance 不可用 | `zcode/quota.go` `fetchAccountQuota` |
| 渲染 | 进度条 `width:100%` 硬编码，不随用量变化 | `zcode/panel.html` `quotaHTML` |

## 四、修复

- `fetchAccountQuota` 改为**主走 balance**（携带设备三头 + `app_version`），失败回退 current；快照新增 `total_used` / `total_remain` / `has_usage` / `source` 与逐 entitlement 的 `used_units` / `remaining_units` / `available_units` / `has_usage`。
- 面板进度条改为按「剩余/授予」渲染（≤30% 转黄、≤10% 转红），卡片与汇总区展示「已用/剩余」；无用量通道时明确标注「每日授予额度（暂未取到用量）」并以半透明满格条区分。

## 五、验证

- 生产实测：修复路径对真实账号产出真实用量（见 2.2 表）。
- 回归守卫：`TestFetchAccountQuota_ParsesBalanceUsage`（校验设备三头、`app_version`、逐 entitlement 用量并入）；哨兵变异（把 balance 通道 `withUsage` 由 true 改 false）后该测试**精确 FAIL**（`expected balance source with usage, got source="current" has_usage=false`），证明真实进编译。
- 回退守卫：`TestFetchAccountQuota_ParsesPlan` 验证 balance 返回 3001 时自动回退 current 且 `Source=="current"`、`TotalRemain==TotalGrant`。

## 六、附带修复（同轮）：领取失败 `no permission` 提示

- **现象**：面板点「🎁 领取额度」后 toast 显示「领取失败 / claim failed: no permission」。
- **根因**：上游 `billing/preview` 当前对**所有**账号返回 `plans:[]`（未下发可领取计划，实测换 `app_version` / `platform` 无关），此时 claim 走 fallback planId 被上游业务层拒为英文 `no permission`。属**上游活动态**而非插件缺陷。
- **修复**：新增 `friendlyClaimError()` 把 `no permission` / `1003 already exists` / `1001 target not found` 翻译为可读中文，未知错误保留原文便于排障；面板对「未开放」类降级为 warn 提示。
