# zcode-provider 面板无感验证未传 captcha 配置致参数无效根因诊断

## 一、问题描述

- **现象**：0.1.28 面板点「🎁 领取额度」后，无感验证看似执行完成，但产出的 `captchaVerifyParam` 仅 **76 字符**且**不含 `securityToken`**；带该参数重调 `/claim` 仍返回 `captcha_required:true`（即 captcha 层未通过），用户侧表现为「点了没反应 / 一直提示需要安全验证」。
- **发现方式**：2026-10-14 生产端到端领取实证（本会话），对「已授权未领取」干净账号走完整链路时暴露。
- **结论（本诊断）**：**面板实现缺陷**。`panel.html` 的 `runTracelessVerification` 既**未在 `initAliyunCaptcha` 入参传 `prefix` / `region`**，又**只设了错误的全局变量名** `window.AliyunRequestVerificationConfig`（SDK 实际读取 `window.AliyunCaptchaConfig`），导致 SDK 把验证请求打到 `undefined.captcha-open.aliyuncs.com`，产出的参数在 captcha 层即被拒。

## 二、证据链（生产 + 真实浏览器，A/B/C/D/E 五组受控实验）

实验环境：真实 Chrome（`user-browser-use`）、官方 SDK `https://o.alicdn.com/captcha-frontend/aliyunCaptcha/AliyunCaptcha.js`、真实场景 `SceneId=11xygtvd`。每组前均刷新页面，避免实例污染。

| 组 | 条件（差异点） | 参数长度 | 含 `securityToken` | SDK 回调 | 判读 |
| --- | --- | --- | --- | --- | --- |
| **A** | 复刻 0.1.28 生产实现：仅设 `AliyunRequestVerificationConfig`，init **不传** `prefix`/`region` | **76** | **否** | `onError:{"code":"INIT_FAIL"}` | ❌ 复现线上缺陷 |
| **B** | init **显式传** `prefix:'no8xfe'` + `region:'sgp'` | **280** | **是** | `getInstance` → `started` | ✅ 成功 |
| **C** | 加载 SDK **前**同时设 `AliyunCaptchaConfig` + `AliyunRequestVerificationConfig`，init 不传参 | **280** | **是** | `getInstance` → `started` | ✅ 成功 |
| **D** | 加载 SDK **前**仅设 `AliyunCaptchaConfig`，init 不传参 | **280** | **是** | `getInstance` → `started` | ✅ 成功（**决定性**） |
| **E** | 加载 SDK **前**仅设 `AliyunRequestVerificationConfig`，init 不传参 | **76** | **否** | `onError:{"code":"INIT_FAIL"}` | ❌ 与 A 同 |

**决定性判读**：

- D 组成功、E 组失败，**唯一差异是全局变量名**：`AliyunCaptchaConfig` 有效，`AliyunRequestVerificationConfig` 无效 → 面板设错了全局名。
- B 组（init 显式传参）无需任何全局变量即成功 → **init 入参 `prefix`/`region` 是权威来源**，也是最稳的修法。

```js
  var On = window.AliyunCaptchaConfig;
  var Pn = On.region || "cn";
  var jn = { prefix: On.prefix || "", region: Pn, ... };   // 只在脚本加载时读取一次
  ...

```

`initAliyunCaptcha` 参数解析（`function en(t,e)`）：

```js

  var r = e.prefix, ...;     // init 入参的 prefix 优先

```

**判读**：SDK 读的是 `window.AliyunCaptchaConfig`（且**仅在脚本加载时读取一次**）；`initAliyunCaptcha` 入参亦可直接提供 `prefix`。0.1.28 面板两处都没做对。


### 2.3 上游接受度对照（同一账号 `zcode-3f656fef06ccd323`）

| 参数来源 | 长度 | `/claim` 上游响应 | 判读 |
| --- | --- | --- | --- |
| 缺陷形态（A/E，76 字符） | 76 | `captcha_required:true`（仍是 captcha 层） | ❌ 参数被 captcha 层拒绝 |

## 三、根因

`zcode/panel.html` 的 `runTracelessVerification(cfg)`：

1. 只写 `window.AliyunRequestVerificationConfig = {region, prefix}`——**SDK 不读这个名字**（SDK 读 `window.AliyunCaptchaConfig`），且该赋值发生在 SDK **加载之后**，即使名字对了也赶不上 SDK 的加载期读取。
2. `window.initAliyunCaptcha({...})` **未传 `prefix` / `region`**——丢掉了最权威、与时机无关的入参通道。

**一句话**：既没设对全局名，也没走 init 入参，SDK 拿不到 `prefix`，请求打到 `undefined.captcha-open.aliyuncs.com`，参数在 captcha 层即失效。

## 四、修复方案（待实施）

`zcode/panel.html` 的 `runTracelessVerification`：

- **主修**：在 `window.initAliyunCaptcha({...})` 入参中**补 `prefix` 与 `region`**（取自 `cfg.prefix` / `cfg.region`，带与全局一致的兜底值）。此为入参通道，与脚本加载时机无关，B 组已实证可用。
- **加固**：把全局变量名由 `AliyunRequestVerificationConfig` **改为 `AliyunCaptchaConfig`**，并**移到 SDK 加载之前**设置（D 组实证有效），作为双保险。
- 保留既有 `button` 元素（预研已证必需）。
- 同步修正 `panel.html` 内联注释，说明 SDK 读取的全局名与加载期语义。

**验证方式**：

- 本地：`python scripts/cgo-shim-build.py zcode` build/vet/test 全绿；面板 JS `node --check` 双 script 块通过。
- 生产：部署后对干净账号走完整链路，断言参数长度 ≥200 且含 `securityToken`，`/claim` 上游响应从 `captcha_required` 变为业务层响应。

## 五、影响面

- **仅影响面板内无感验证领取**（0.1.28 新增能力）；额度查询、模型清单、OAuth 授权、推理链路均不受影响。
- 后端 `claimAccountStartPlan` 的 `plan_id` 动态解析、`X-Device-Mid` 设备指纹**均已正确**（本会话已复验），无需改动。
- 修复为**单文件前端改动**（`panel.html` 一个函数），风险低。

## 六、上游状态补充说明（与本缺陷无关）

- 本会话盘点生产 8 账号：4 个已激活（`plan_status=active`、`total_grant=8000000`），3 个「无生效计划」。
- 对 3 个未领取账号调上游 `billing/preview`：**全部返回 `code:0` 但 `plans:[]`（空）**，换 `app_version`（`3.15.1` / `unknown` / `3.15.1.8093`）结果一致。
- 判读：上游当前**未下发任何可领取计划**，故 `claim` 业务层返回 `no permission`。这是**上游账号/活动态**，不是插件缺陷，也不阻塞本 Bug 的修复与验证（captcha 层已可独立判据）。

## 七、附：与预研文档的差异

预研文档 `doc/5-tests/2026-10-14_151500_zcode无感验证领取额度可行性预研.md` 2.1 节记录「多轮测试 100% 成功产出 200+ 字符参数」——**该结论成立**，因为预研脚本当时是在页面上下文里手工调用、且 SDK 已在早前加载过程中读过页面自身的 `AliyunCaptchaConfig`。0.1.28 落地为面板函数时未把该前置条件带过去，才产生本缺陷。预研结论与本次诊断不矛盾，属**落地实现遗漏**。
