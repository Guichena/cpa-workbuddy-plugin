# 成长中心接单结果未逐条判定致失败被虚报为成功根因诊断与修复

- Bug 编号：BUG-GROWTH-ACCEPT-RESULTS-IGNORED-20261017
- 发现时间：2026-10-17 00:20（北京时间，用户报告「成长计划好像没有生效, 任务都没有完成」并附成长中心页面 URL）
- 影响范围：workbuddy-provider 0.16.x 的成长中心任务域（`/tasks` 接单链路）的计数与错误上报
- 严重级别：中（功能未失效但**结果失真**：失败被记为成功，用户无法自查原因，且面板显示误导）
- 状态：**已定位 / 已修复（0.16.3）**

## 1. 现象

用户报告：成长计划未生效，任务都没有完成（`workbuddy.cn/profile/growth-center`）。

生产日志交叉印证（`docker logs cli-proxy-api`，近 48h）：

| 时间 | 账号 | 日志行 |
| --- | --- | --- |
| 10-16 04:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |
| 10-16 08:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |
| 10-16 12:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |
| 10-16 16:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |
| 10-16 20:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |
| 10-17 00:00 | 700fd592 | `+0 credits, +0 energy, 14 accepted, 0 claimed, 1 errors` |

**关键指纹**：`14 accepted` 连续 6 轮**数值恒定不变**。若接单真生效，下一轮 pending 集合必然收敛（任务状态推进到 accepted/completed），`accepted` 应降为 0。恒定不变说明接单请求**从未真正成功**，但插件每轮都记为 14 项成功。

同一账号每轮伴随 `growth POST /buddy/travel/depart failed ... code=400 msg=no active buddy` —— 与 EXT-1 契约注释点名的前置条件失败同源。

对照组：同批次账号 `912daf78` 于 10-16 20:00 报 `+200 credits, +10 energy, 0 accepted, 2 claimed, 0 errors` —— 证明**领奖链路本身通畅**，缺陷局限于接单结果判定。

## 2. 根因

### 2.1 直接原因：接单只看 HTTP 状态码，不读上游逐条 `results`

上游 `/tasks/accept` 对「前置未满足」的任务返回 **HTTP 200 + envelope `code=0`**，把单条失败写在 `data.results[i].status = "error"`（典型 `message` 为 `prerequisite not met: first_buddy (no buddy instance found)`）。

而 `workbuddy/growth.go` 的 `acceptGrowthTasks` 原实现只校验传输层与 envelope 层：

```go
m, err := growthPostMap(sa, growthPathTasksAccept, map[string]any{"task_codes": codes[start:end]})
if err != nil {
    return out, err
}
out = append(out, m)      // ← 只要没报错就当整批成功
```

调用方随之按「发出的任务码数量」记账：

```go
if _, acceptErr := acceptGrowthTasks(sa, pending); acceptErr != nil {
    res.Errors = append(res.Errors, "tasks_accept: "+acceptErr.Error())
} else {
    res.TasksAccepted += len(pending)   // ← len(pending) 是请求量，不是成功量
}
```

于是 14 项全被上游逐条拒绝时，插件仍报 `14 accepted, 0 errors`。

**契约对照**：EXT-1（`88lin/workbuddy-auto-signin` 的 `signin.py`）在接单段有明确注释：

> 逐条读 results：接单失败必须报出来（常见 "prerequisite not met: first_buddy (no buddy instance found)"），**静默吞掉的话接口坏了也没人知道——轮询空跑是不写日志的**。

并逐条判定 `r.get("status") == "error"` 后计数失败。插件转写时只保留了「发请求」，丢失了「读结果」。

### 2.2 为什么单测没拦住

既有测试桩的 `/tasks/accept` 响应固定为 `{"results":[]}`（空数组）：

```go
case growthPathPrefix + growthPathTasksAccept:
    return `{"code":0,"msg":"OK","data":{"results":[]}}`
```

空 `results` 下任何实现都「成功」，断言 `TasksAccepted != 1` 也无法区分「按请求量计」与「按逐条结果计」。测试桩未覆盖「`results` 含 `status=error` 条目」这一真实形态。

### 2.3 为什么用户无法自查

- 定时 tick 日志只打错误**条数**（`%d errors`），不打原因 → 用户看不到「为什么任务没完成」；
- 面板摘要行在无收益时固定显示「今日已领完」→ 即使有失败也掩盖成「无事可做」。

## 3. 修复（0.16.3）

### 3.1 逐条判定接单结果

`acceptGrowthTasks` 返回值由 `[]map[string]any` 改为结构化汇总 `growthAcceptOutcome`：

```go
type growthAcceptOutcome struct {
    Accepted int
    Errors   []string
}

// results 存在时逐条判定；缺失或为空时回退整批成功（不把契约省略当成失败）
results, ok := m["results"].([]any)
if !ok || len(results) == 0 {
    out.Accepted += len(batch)
    continue
}
for _, raw := range results {
    item, _ := raw.(map[string]any)
    if jsonStr(item, "status") == "error" {
        failByReason[jsonStr(item, "message")]++
        continue
    }
    out.Accepted++
}
```

失败原因**按 message 聚合**（附条数），避免 14 条逐项铺开撑爆面板 toast 与日志；原因文本统一经 `truncateRedacted` 脱敏截断。

### 3.2 调用方改用真实成功数

```go
out, acceptErr := acceptGrowthTasks(sa, pending)
res.Errors = append(res.Errors, out.Errors...)
if acceptErr != nil {
    res.Errors = append(res.Errors, "tasks_accept: "+acceptErr.Error())
} else if out.Accepted > 0 {
    res.TasksAccepted += out.Accepted
    res.Segments = append(res.Segments, "tasks_accept")
}
```

### 3.3 错误原因可见化

- 定时 tick 日志：在既有汇总行后逐条打印 `[workbuddy] growth error for <uid>: <原因>`，使「任务未完成」可自查；
- 面板摘要行：有失败原因时显示「N 项失败」而非「今日已领完」，与 toast 的失败明细一致。

## 5. 边界说明（非插件缺陷部分）

**任务「未完成」本身包含上游业务前置**：EXT-1 与插件均只有 `/tasks`（列表）、`/tasks/accept`（接单）、`/tasks/{code}/claim`（领奖）三个端点，**不存在「完成任务」端点**——任务的 `completed` 状态依赖用户在 WorkBuddy 客户端真实操作（如每日对话任务需实际发起对话）。插件能力边界是「自动接单 + 自动领奖」，无法代替用户完成动作。

因此本修复不改变「任务是否会被上游标记 completed」，只修正**插件对自身动作结果的陈述真实性**：把「接单失败」如实报出来，让用户能区分「无事可做」与「做了但被拒」。

## 6. 教训

1. **写端点返回 200 + code=0 不等于业务成功**：批量写接口常在 `data.results[i]` 里逐条表达成败，只看传输层会把部分失败整批虚报为成功。凡上游提供逐条结果，必须逐条消费。
2. **计数口径要区分「请求量」与「成功量」**：`len(pending)` 是意图，`results[i].status` 才是事实。日志里的「N accepted」必须来自事实。
3. **测试桩要覆盖失败形态**：桩只返回成功形态时，任何实现都能通过。接单桩必须至少含一条 `status=error`。
4. **「恒定不变的计数」是强指纹**：连续多轮同一数值意味着状态机没有推进，是定位「请求发了但没生效」类缺陷的关键线索。
5. **可自查性属于功能的一部分**：只打错误条数不打原因，会让用户与维护者都失去定位能力；错误原因必须随日志与面板可见。
