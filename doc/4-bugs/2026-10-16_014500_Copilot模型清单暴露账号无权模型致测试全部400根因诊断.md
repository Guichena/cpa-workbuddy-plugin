# Copilot 模型清单暴露账号无权模型致面板测试全部 400 根因诊断

- Bug 编号：`BUG-COPILOT-MODEL-ENTITLEMENT-20261016`
- 发现日期：2026-10-16
- 影响插件：`copilot-provider`（0.1.3 及以前）
- 严重级别：High（功能可见但不可用：面板暴露 25 个模型，用户逐个测试全部失败）
- 状态：根因已定位，待修复

## 一、现象

用户在生产面板「测试模型」弹窗对 25 个模型逐个测试，**没有一个通过**。典型失败：

```
测试失败 (HTTP 400): upstream status 400:
{"error":{"message":"The requested model is not supported.",
  "code":"model_not_supported","param":"model","type":"invalid_request_error"}}
```

同一现象在 0.1.3 之前的生产日志中已存在（当时未联系）：

```
[2026-10-15 22:14:13] upstream execution failed: provider=copilot-provider
  model=claude-sonnet-4 ... err=upstream error 400: {...model_not_supported...}
```

## 二、取证过程（生产账号 `copilot-f13aadb583ef01ba`，`sku=free_limited_copilot`）

对上游 `/models`（`Copilot-Integration-Id: vscode-chat`，返回 56 条）过滤后得到 25 个候选，

**结论：25 个候选中，仅 10 个真正可走 `/chat/completions`**（本插件唯一转发端点，见 `executor.go:246`），
15 个报 400 `model_not_supported`。

### 2.2 静态字段判别器失效（关键否证）

对 25 个候选的全部字段路径（`capabilities.*` / `policy.*` / `supported_endpoints` / `vendor` /
`model_picker_enabled` / `version` / `preview` / `name` / `limits.*`）做「可用集合 vs 不可用集合」交叉判别，
**唯一无交集的字段是 `.id`**（同义反复，不构成判据）。

- `supported_endpoints` 含 `/chat/completions` 的条目（kimi-k3-*、gpt-5-mini、claude-haiku-4.5）**仍报 400**；
- `supported_endpoints` 为 `null` 的条目（gpt-4o、gpt-4o-mini、gpt-4.1、gpt-4）**部分 200、部分 400**；
- `policy.state` 为 `enabled` 的条目（gpt-5.6-luna、gpt-6-luna、kimi-k3-*、mai-code-*、gpt-5-mini）**全部 400**。

即：**上游 `/models` 返回的是「该账号可见」而非「该账号可调用」的模型全集**，
其响应中不存在任何能区分「可调用性」的静态字段。

### 2.3 零消耗探测法（可行性验证）

构造 `POST /chat/completions`，body 仅 `{"model": "<id>"}`（**省略 messages**）：

- 可调用模型 → `400 {"error":{"message":"messages must be non-empty","code":""}}`；
- 不可调用模型 → `400 {"error":{"message":"The requested model is not supported.",...}}`。

配额对照（`api.github.com/copilot_internal/user` 的 `quota_snapshots`）：

```
BEFORE: {'chat': (200, 200), 'completions': (1963, 2000), 'premium_interactions': (0, 0)}
AFTER : {'chat': (200, 200), 'completions': (1963, 2000), 'premium_interactions': (0, 0)}
```

**配额零消耗**：请求在模型鉴权阶段即被拒绝，未进入推理计费。

并发 6 探测 25 个模型耗时 **3.38s**（`ThreadPoolExecutor(max_workers=6)`）。

### 2.4 集成标识对清单的影响（备选线索，非根因）

`Copilot-Integration-Id: copilot-chat` 返回 48 条（vs `vscode-chat` 56 条），差异集中在
实验模型（`gemini-3.7/3.8-flash`、`gpt-5.4-nano`、`kimi-k3-*`、`mai-code-1-flash-4th` 等）。
换用该标识**不改变可用性根因**（仍含大量不可调用模型），故不作为修复方向。

## 三、根因

`fetchUpstreamModels`（`models.go:134`）以「`capabilities.type=chat` + `policy.state != disabled` +
非内部工具项」为过滤判据，把上游 `/models` 的 56 条收敛为 25 条并对外暴露。

**该判据只能过滤「类型与策略」，无法过滤「账号 entitlement」**：
免费档 `free_limited_copilot` 的 `/models` 响应包含大量本账号无权调用的模型（如全部
`gpt-5.x` / `gpt-6-luna` / `claude-haiku-4.5` / `kimi-k3-*` / `mai-code-*`），
而响应中**无任何静态字段**可标记这一差异。

结果：插件把 25 个「可见」模型当作「可用」模型暴露给面板与宿主，
用户点击测试即命中上游 400，形成「面板显示一堆模型、一个都测不通」的现象。

## 四、修复方案（已实施，0.1.4）

1. **新增零消耗可用性探测**（`models.go` 的 `probeUsableModels` / `probeModelCallable`）：
   动态发现后对候选模型并发（≤6）发一次 `{"model": id}` 无 messages 请求，
   仅保留返回 `messages must be non-empty`（或 2xx）的模型。探测结果随模型缓存一起按 TTL 缓存。
2. **探测失败降级**：单个探测遇传输错误 / 5xx 时保守保留该模型；探测整体无结果时
   回退到 `/models` 过滤清单（宁多勿空），不因探测故障清空模型出口。
3. **整批总预算**：`probeBatchBudget = 25s`，上游探测中途不可达时未完成的按「保留」处理，
   避免 25 模型 × 15s 客户端超时把面板请求拖到分钟级。
4. **同步落盘**：探测后的清单刷新账号 `models` 字段，避免 `modelCache` 过期后
   面板卡片回落到历史兜底清单、与测试弹窗不一致。
5. `/responses` 端点模型（`gpt-5.4-nano` 类）因本插件只转发 `/chat/completions`，
   探测失败后被自然剔除。

## 六、影响面

- 面板「测试模型」：用户逐个测试失败率 15/25。

- 调度器候选集：暴露了不可用模型 ID，可能被选为候选并失败。
