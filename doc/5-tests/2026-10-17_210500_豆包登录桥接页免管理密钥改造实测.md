# 豆包登录桥接页免管理密钥改造实测（0.1.4）

- 日期：2026-10-17
- 插件：`doubao-provider`（0.1.3 → 0.1.4）
- 来源：用户反馈「为什么还要管理密钥控制呢？我们 trae 也是这样的授权步骤就不需要」
- 结论：已改为与 traework 同构的免密钥 resource 路由提交，单测 + 真实 `.so` ABI 探针全绿

---

## 一、问题

0.1.3 的登录桥接页让用户粘贴 Cookie 后，浏览器直接请求：

```
POST /v0/management/plugins/doubao-provider/import
Authorization: Bearer <管理密钥>
```

而宿主对 `/v0/management/*` 强制鉴权，于是桥接页必须再要求用户填写管理密钥——
用户截图里就是这个红框：「管理密钥无效或已失效，请重新填写」。

traework 的同类授权步骤完全不需要密钥，体验明显更好。

## 二、根因

不是「密钥填错了」，而是**提交通道选错了**：

| 插件 | 桥接页提交方式 | 是否需要密钥 |
|---|---|---|
| traework | 提交回 `GET /v0/resource/plugins/<id>/browser-login/bridge?url=...`，服务端完成导入 | 不需要 |
| 豆包 0.1.3 | `POST /v0/management/plugins/<id>/import`，浏览器直连管理路由 | **需要** |

宿主的 resource 路由（`/v0/resource/plugins/<id>/*`）是**免鉴权**的，但它只放行 GET
且不转发请求体（`ServeResourceHTTP` 里 `if !strings.EqualFold(r.Method, http.MethodGet) { return false }`）。
豆包当时没走这条路，所以只能落到需要鉴权的 management 路由上。

## 三、修复

### 3.1 新增免密钥提交路由

`Resources` 新增 `/login/import`；桥接页把 Cookie 放进自定义请求头
`X-Doubao-Cookie`（resource 路由不转发 body，只能用请求头），state 走 query：

```
GET /v0/resource/plugins/doubao-provider/login/import?state=<state>
X-Doubao-Cookie: <完整 Cookie header>
```

### 3.2 安全性：state 就是一次性凭证

不需要管理密钥不等于没有鉴权。`state` 在 `auth.login.start` 时随机生成
（`randomUUID()`），15 分钟过期，且只对发起登录的那个会话有效——它等价于
一次性的短时凭证，作用域仅限「导入一个账号」。

拿到有效 state 的人本来就能完成这次登录（这也是 OAuth 的常规语义），
不存在越权读取或修改已有账号的路径：该入口只能新增账号，不能列举、删除或禁用。

### 3.3 清理

- 移除桥接页的管理密钥输入框、`localStorage` 密钥读取、401 清 key 逻辑；
- `/import` 管理路由不再承担桥接页回传职责，删除已无调用方的 `login_state` 分支
  （面板自己的「导入」按钮仍走这个路由，行为不变）。

## 四、测试

### 4.1 Go 单元测试

`cgo-shim-build.py doubao` → build + vet + test 全绿。

新增 3 个用例：

| 用例 | 覆盖点 |
|---|---|
| `TestLoginBridgeImportWithoutManagementKey` | 不带 `Authorization` 也能导入，且随后 `auth.login.poll` 返回 success 并回传同一 auth_id |
| `TestLoginBridgeImportRejectsBadInput` | 缺 state / 未知 state / 缺 Cookie 三条拒绝路径均返回 400 且提示可读 |
| `TestLoginBridgeImportRouteIsDispatched` | 走 `handleManagement` 验证路由真的可达 |

### 4.2 变异自测

把 `handleManagement` 里的 `/login/import` 分支改成返回 404：

```
--- FAIL: TestLoginBridgeImportRouteIsDispatched (0.00s)
    login_test.go:530: 提交应成功，实际 404：{"error":"not_found"}
FAIL
```

变异被捕获。注意：**只测 `handleLoginBridgeImport` 函数本身时该变异不会失败**——
函数级用例绕过了分发表，这也是补 `TestLoginBridgeImportRouteIsDispatched` 的原因。

### 4.3 桥接页回归（Node vm）

`node test/doubao/login_bridge_repro.mjs` → 全部通过，关键断言：

- 页面无 `id="key"`、无「管理密钥」文案；
- 提交路径为 `/v0/resource/plugins/doubao-provider/login/import`，携带 state；
- 方法为 GET，Cookie 走 `X-Doubao-Cookie`，**不带 Authorization、不带 body**；
- 成功/失败/会话过期三种结果渲染正确。

### 4.4 真实 `.so` ABI 探针

WSL gcc 构建 `CGO_ENABLED=1 -buildmode=c-shared` 真实 linux/amd64 `.so`
（10,955,832 B），ctypes 驱动 `cliproxy_plugin_init` → `cliproxyPluginCall`：

```
[1] auth.login.start 返回 resource 桥接页 ................. PASS ×3
[2] 缺 Cookie 的提交必须被业务拒绝（不是 401/404） ........ PASS ×4
[3] 未知 state 必须被拒绝 ................................ PASS ×2
[4] 缺 state 必须被拒绝 .................................. PASS ×1
[5] 桥接页 HTML 不再出现管理密钥输入 ...................... PASS ×3
[6] 未导入时轮询必须是 pending（不假成功） ................ PASS ×1

[结果] 14/14 PASS
```

其中 [2] 的三条断言最关键：状态码 400（进入业务逻辑）、**不是 401/403**（没被管理密钥拦下）、
**不是 404**（路由已注册）——直接证明免密钥通道成立。

探针只走拒绝路径，不写入任何账号（已回读确认账号目录为空），也不发送真实凭据。

## 五、发布与生产验收（0.1.4）

### 5.1 CI 与 FreeBSD 阻断

CI run `39035066234`：doubao 的 `Test (doubao)` 与 6 个平台构建全部成功，
**但全部 10 个插件的 `freebsd-amd64 (go-cross)` 同时失败**。

根因不是代码，而是镜像下架：

```
wget https://download.freebsd.org/releases/amd64/14.3-RELEASE/base.txz
→ exit code 4

实测：releases/14.3、old-releases/14.3 均 404
     当前官方仅保留 14.4 / 14.5 / 15.0 / 15.1
```

CI 的 `Patch FreeBSD download mirror` 步骤只是把 `download` 换成 `archive`，
而 archive 同样没有 14.3，所以补丁已失效。这是仓库级基础设施缺陷。

### 5.2 决策与处理

按用户决策「先只发 6 平台」：

- `scripts/publish-assets.py` 引入 `OPTIONAL_PLATFORMS = {"freebsd_amd64"}`：
  存在就登记，缺失只打印 NOTE 不阻断；checksums 与 registry 都按实际存在的平台生成。
- 本轮 registry 登记 6 个平台（darwin/linux/windows × amd64/arm64）。
- CI 的 Release 步骤本来就只校验这 6 个平台，无需改动。
- 镜像版本修好后可重新 dispatch 补发 freebsd 包。

## 六、遗留与边界

1. **FreeBSD 平台暂缺**：CI 的 go-cross 固定请求已下架的 FreeBSD 14.3，导致全仓 10 个插件的 freebsd 构建失败。建议把镜像版本改为 14.4（实测可下载）并重跑，届时可补发 doubao 的 freebsd 包。
2. **真实新账号导入需用户本人操作**：本轮验证到「免密钥通道成立 + 假 Cookie 被上游如实拒绝」，真实账号仍需用户粘贴自己的浏览器 Cookie。
3. **上游 `710022004` 限流未解除**：账号级风控，与本次改动无关。
4. **`saveCredentials` 的 device_id 持久化缺口仍在**（既有，建议单独立项）。
