# 豆包 Provider 重复账号、模型清单与测试失败三问题实测（0.1.5）

- 日期：2026-10-17
- 插件：`doubao-provider` 0.1.4 → 0.1.5
- 触发问题（用户原话）：「豆包导入一个账号的授权, 面板出现了2个账户, 并且模型测试不通过都是失败的, 并且模型也不多, 不是通过api动态获取的吗?」
- 结论摘要：重复账号是插件缺陷（已修）；测试全部失败是上游账号级风控（非插件缺陷，已改提示）；模型清单原为静态别名（已改为动态发现，实测取得 26 个上游模型）。

## 一、问题①：导入一个账号，面板出现两条记录

### 1.1 现象取证（生产只读）

插件账号目录只有 1 个文件，宿主 auth 目录为空（生产用 MySQL spool）：

```text
/root/.antigravity_cockpit/doubao_accounts/doubao-adcd31d29873b4c8.json   (1 个文件)
/CLIProxyAPI/mysqlstore/mysqlstore/auths/doubao-adcd31d29873b4c8.json     (同一账号)
```

但面板 API 返回 2 条完全相同的记录（`auth_id` 相同）：

```text
GET /v0/management/plugins/doubao-provider/accounts
{"accounts":[{"auth_id":"doubao-adcd31d29873b4c8",...},{"auth_id":"doubao-adcd31d29873b4c8",...}],"count":2}
```

宿主 `/v0/management/auth-files` 同样返回 2 条，**物理路径完全相同**，只有 `id` 不同：

| id | auth_index | path |
|---|---|---|
| `doubao-adcd31d29873b4c8.json` | 8c8eb5500e812d49 | .../auths/doubao-adcd31d29873b4c8.json |
| `doubao-adcd31d29873b4c8` | 8c8eb5500e812d49 | .../auths/doubao-adcd31d29873b4c8.json |

### 1.2 根因（宿主 SDK v7.2.129 源码取证）

宿主有两条注册路径，派生的 Auth ID 口径不同：

1. **文件扫描 / `host.auth.save`**：`synthesizeFileAuths`（`internal/watcher/synthesizer/file.go`）
   与 `Host.authIDForPath`（`internal/pluginhost/auth_callbacks.go:504`）都用
   **相对 auth 目录的路径**作 ID → `doubao-xxx.json`（带扩展名）。
2. **登录结果落盘**：`savePluginLoginRecords` → `AuthDataToCoreAuth`
   （`internal/pluginhost/auth_provider.go:537`）优先使用 `data.ID` **原样**作 ID。

插件 `authDataForLogin` 回传 `ID: sa.AuthID`（不带 `.json`），于是同一个物理文件被
注册成 `doubao-xxx` 与 `doubao-xxx.json` 两个 ID。`Manager.Register` 按 ID 去重
（`m.auths[auth.ID] = authClone`），ID 不同即视为两个账号。

插件侧 `listAllAuthFiles` 的本地分支有 `if !exists` 判重，但宿主分支直接 `append`，
因此重复记录被原样透出到面板。

### 1.3 修复

| 落点 | 改动 |
|---|---|
| `doubao/login.go` `authDataForLogin` | `ID` 改为 `authFileNameOf(sa.AuthID)`，与 `FileName` 同形（带 `.json`）；新增 `authFileNameOf` 归一化，已带后缀不叠加 |
| `doubao/login.go` `handleParseAuth` | 回传的 `Auth.ID` 显式设为 `req.FileName`，避免同一次扫描既登记路径 ID 又登记裸 ID |
| `doubao/authfile.go` | 新增 `dedupeAuthByID`，`listAllAuthFiles` 对宿主来源按 `AuthID` 去重，兜住旧版本已写进宿主的历史重复项 |

### 1.4 变异测试（确认用例真能抓到）

| 变异 | 期望 | 实测 |
|---|---|---|
| 去掉 `dedupeAuthByID` 的判重 | 去重用例失败 | `FAIL: TestListAllAuthFilesDedupesByAuthID ... 应保留 2 个不同账号，实际 3` |
| `AuthData.ID` 改回 `sa.AuthID` | 4 个用例失败 | `FAIL: TestAuthDataIDMatchesHostFileName ... ID="doubao-idform0001" FileName="doubao-idform0001.json"` |

## 二、问题②：模型测试全部失败

### 2.1 现象

生产 `POST /test-active` 返回：

```json
{"error":"测试失败（模型: doubao/default）：上游限流，请稍后重试","model":"doubao/default"}
```

### 2.2 对照探测（排除三类常见误判）

用生产账号 Cookie 直接打 `/chat/completion`，只读、不回显凭据：

| 组 | 出口 IP | device_id | web_id | web_tab_id | 结果 |
|---|---|---|---|---|---|
| A | 本机（国内） | 空 | 空 | 空 | `710022004 semantic_reasoning` |
| B | 生产服务器 | 空 | 空 | 空 | `710022004 semantic_reasoning` |
| C | 生产服务器 | 空 | 有 | 空 | `710022004 semantic_reasoning` |
| D | 生产服务器 | 有 | 有 | 有 | `710022004 semantic_reasoning` |
| E | 本机 | 深度思考 ndt=1/udt=1 | — | — | `710022004 semantic_reasoning` |
| F | 本机 | 非法值 ndt=999 | — | — | `710022004 semantic_reasoning` |

结论：**与出口 IP、设备标识、深度思考参数均无关**，是账号级风控。

同时验证账号本身有效：

```text
GET https://accounts.doubao.com/passport/account/info/v2/ → message="success"，sec_user_id 非空
```

即：登录态有效、账号信息端点正常，只有推理链路被拦截——与既有实测记录
（`710022004` 由 `shark_admin/verify/semantic_reasoning` 下发，持续 20+ 分钟未解除）
完全一致。

### 2.3 处置

不改判定逻辑（本就正确识别为限流），只把提示改成可操作文案：
`710022004/710022005` 现在说明「账号触发上游风控（semantic_reasoning），非网络问题；
请换用其他账号或等待风控解除（账号信息与登录态本身仍有效）」。

同步更新两处依赖旧文案的断言（`completion_test.go`、`active_ping_test.go`）。

## 三、问题③：模型不多，不是动态获取的吗

### 3.1 原设计（CYCLE-05 既定决策）

`capabilityAliases` 是 4 个静态能力别名（`default` / `pro` / `image` / `video`），
`textModelIDs()` 只返回 `Skill == 0` 的两条 → 测试弹窗里只有 `doubao/default`、`doubao/pro`。
原设计理由是上游 `model_list` 的 `name` 是不可读内部代号。

### 3.2 上游真实结构（本次实测）

```text
/alice/basic/launch → data.model_list：67 条
去重后 name：26 个（Aoe 出现 27 次但 model_type 各不相同）
样本：Aoe / anceba / anceba an / ances brs / ances s2 / ogt / ogf / xmm / xnm
     func: ogf（8k）/ func: ogt（16k）/ func: ogt（4k）
字段：{model_name, model_type, name, support_pic_gen_switch, support_web_search_switch, typewriter_switch}
```

即：代号不可读但**可用**（上游真正认这些名字）。经用户裁定采用「动态透传上游内部代号」。

### 3.3 实现

新增 `doubao/model_discovery.go`：

- `discoverUpstreamModels`：POST `/alice/basic/launch`，解析 `model_list`；
- `modelsFromUpstream`：按 `name` 去重（同名不同 `model_type` 只暴露一个名字），按名字排序；
- `cachedUpstreamModels`：**按账号隔离**缓存，TTL 10 分钟，`force` 绕过；
- `upstreamModelDescription`：如实标注「上游模型代号 X（model_type=N）…无公开可读名」。

接入点：

| 位置 | 行为 |
|---|---|
| `handleModelsQuery`（面板测试弹窗） | 优先上游清单；失败回落能力别名并带 `source=fallback` + `notice` 说明原因 |
| `modelForAuth`（宿主按账号目录） | 能力别名在前 + 上游模型去重合并；上游不可达时只返回别名 |
| `modelStatic`（宿主启动期） | 保持不变，只返回能力别名（此时可能还没有账号） |
| `panel.html` | 显示回落原因；新增「刷新模型清单」按钮（`force=1`） |

### 3.4 真实账号验证（真实 `.so` + C ABI）

```text
[账号] auth_id=doubao-adcd31d29873b4c8
[结果] HTTP 200  source=upstream  模型数=26
   doubao/4tbp / doubao/anceba / doubao/anceba an / doubao/ances brs / ...
   doubao/func: ogf（8k）/ doubao/func: ogt（16k）/ doubao/func: ogt（4k） / ...
[结果] 动态发现通过：从上游取得 26 个模型
```

## 四、附带发现：doubao/pro 深度思考尚未真正生效

`buildCompletionRequest` 里 `need_deep_think=0`、`ext.use_deep_think="0"`、
`model_item_key="0"` 全部硬编码，`doubao/pro` 与 `doubao/default` 发出的上游请求完全相同。

风控期无法做参数消融（见 §2.2 组 E/F 均被限流），因此**未改动参数**，按用户裁定
在 `pro` 的 `Description` 里如实标注「当前版本与 default 发出的上游请求相同……深度思考尚未真正生效」。

## 六、未覆盖与后续

1. **生产重复记录的实际清理**：修复保证新导入不再产生重复；已存在的两条记录需要
   重新导入或手动删除一次，本轮未在生产上删除用户账号数据。
2. **深度思考参数**：需等风控解除后做 `need_deep_think` / `model_item_key` 的真实消融，
   才能让 `doubao/pro` 名实相符。
3. **上游代号的可读名**：`model_list` 不含展示名，若后续从其他端点拿到映射可再补充说明。
4. **模型名能否真正选中上游模型**：`model_item_key` 仍为 `"0"`，透传的代号目前只解决
   「模型可见」，是否真正切换上游模型同样需要风控解除后验证。
