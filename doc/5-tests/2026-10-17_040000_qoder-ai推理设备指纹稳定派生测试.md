# qoder-ai 推理设备指纹稳定派生测试

结论：qoder-ai 推理链路的设备标识（`cosy-machineid`/`cosy-machinetoken`/`cosy-machinetype`）由「每次会话随机 UUID」改为「按账号 UID 稳定派生」，同一账号跨 token 刷新与进程重启保持恒定，多账号互相隔离，且命名空间与 qoderwork 插件隔离；影响：生产 qoder-ai 账号的推理请求在服务端呈现为稳定且互不相同的虚拟设备，消除每约 4 小时 token 刷新导致的设备标识漂移（与 qoderwork 0.9.41 同款修复）；范围：`qoder-ai/sign.go`；非范围：未改会话密钥（仍随机）、未改上游协议与签名算法、未改 UMID 活动链路（`umid.go`/`umid_codec.go`/`umid_crypto.go`）、未改 qoderwork；变化：同账号 `cosy-machineid` 在会话重建前后一致；完成标准：Go 测试全绿 + 双哨兵正交精确 FAIL + 形态兼容；术语说明：设备指纹指上游用于识别「同一台物理设备」的三个 `cosy-machine*` 请求头；验证状态：本地真实测试完成，生产验证待发布。

- 缺陷同构证据：改动前 `qoder-ai/sign.go` 的 `newCosySession` 与 `qoderwork/sign.go` 修改前**逐字节同构**（段落 md5 一致：`33349715c93be5ce1043cb2f841129ed`）
- 漂移触发点：`invalidateCosySession` 在 `keepalive.go:160`、`oauth.go:542`、`oauth.go:563` 三处被调用（token 刷新即重建会话），原实现每次重建都 `uuid.NewString()` → 设备标识随之漂移

## 2. 两条设备标识链路的关系（关键前提）

qoder-ai 存在两条**互不相关**的设备标识链路，本轮只改第一条：

| 链路 | 文件 | 用途 | 标识来源 | 本轮是否改动 |
| --- | --- | --- | --- | --- |
| 推理 COSY 链路 | `sign.go` 的 `newCosySession` | 推理请求的 `cosy-machineid`/`token`/`type` 三头 | 原为随机 UUID（**缺陷**） | **是**（改为 UID 稳定派生） |
| 活动 UMID 链路 | `umid.go` 的 `resolveAccountUMID` | 活动 API 的 6 个 `Cosy-Machine*` 头 | 真实远端桥 `us-pum.alibabachengdun.com` 签发的 `P1gA...` 令牌（**已稳定**） | 否 |

- 依据：`umid.go:122` 的 `refreshAccountUMID` 通过远端桥获取真实令牌并缓存（TTL 12h），`umid.go:162` 的 `MachineID` 已是 `uuid.NewSHA1(uuid.NameSpaceDNS, seedKey)` 稳定派生；该链路 2026-10-11 已实现按账号隔离与 `SAME_PERSON` 轮换（见 `qoder-ai/CHANGELOG.md` 0.1.18 条目）。
- 结论：**活动链路无同款缺陷**，本缺陷只在推理链路。

## 4. 实现要点

| 项 | 实现 |
| --- | --- |
| 种子 | `cosyFingerprintSeed(id)`：UID 优先 → 访问令牌 → `"anonymous"` 占位 |
| MachineID | `uuid.NewSHA1(uuid.NameSpaceOID, "qoderai:machine:"+seed)` → **保持 UUID 形态** |
| MachineToken | `base64.RawURLEncoding(sha512("qoderai:machinetoken:"+seed))[:43]` → **保持 43 字符 base64url** |
| MachineType | `hex(sha256("qoderai:machinetype:"+seed))[:18]` → **保持 18 位十六进制** |
| TempKey / Info | **保持随机**（非设备标识，仅用于加密身份载荷） |

**与 qoderwork 的唯一差异**：命名空间前缀 `qoderai:` vs `qoderwork:`，保证同一 UID 在两插件下派生不同标识（见用例 `TestDeriveMachineIdentity_IsolatedFromQoderWork`）。

**形态兼容性设计**：三种派生值刻意复刻原随机值的形态（UUID / 43 字符 base64url / 18 位 hex），以对冲「上游对 `cosy-machineid` 有格式校验」的风险。

## 5. 用例与断言

| 用例 | 断言 | 防的是什么 |
| --- | --- | --- |
| `TestDeriveMachineIdentity_StableForSameUID` | 同 UID 两次构造的三项设备标识完全相同，且 TempKey/Info 仍不同 | 指纹漂移；且防「把会话密钥也固定化」的过度修改 |
| `TestDeriveMachineIdentity_IsolatedAcrossAccounts` | 不同 UID 的三项设备标识互不相同 | 多账号被判同设备 |
| `TestDeriveMachineIdentity_ShapeCompatible` | UUID 正则 / 43 字符 / base64url 字符集 / 18 位 hex | 形态变化致上游格式校验拒绝 |
| `TestCosyFingerprintSeed_FallbackChain` | UID 优先、缺 UID 用令牌、皆空返回占位 | 种子缺失致 panic 或串号 |
| `TestDeriveMachineIdentity_TokenChangeKeepsFingerprint` | 同 UID 下令牌变化不影响三项设备标识 | token 刷新（会话重建主因）导致漂移 |
| `TestDeriveMachineIdentity_IsolatedFromQoderWork` | 同 UID 下本插件派生值 ≠ qoderwork 命名空间派生值 | 跨插件命名空间冲突致误判同设备 |

### 6.2 双哨兵正交变异（判别力验证）

**哨兵 1**：`machineID := deriveMachineID(seed)` → `uuid.NewString()`（退回随机）

```
--- FAIL: TestDeriveMachineIdentity_StableForSameUID (0.00s)
    sign_fingerprint_test.go:25: 同账号 MachineID 应恒定，got "2e8d72fa-..." vs "b02ef3fe-..."
--- FAIL: TestDeriveMachineIdentity_TokenChangeKeepsFingerprint (0.00s)
    sign_fingerprint_test.go:116: 令牌刷新不应改变设备标识
FAIL
```

**哨兵 2**：种子忽略 UID（`return uid` → `return "fixed-seed"`）

```
--- FAIL: TestDeriveMachineIdentity_IsolatedAcrossAccounts (0.00s)
    sign_fingerprint_test.go:54: 不同账号 MachineID 不应相同，均为 "cdff2dab-..."
--- FAIL: TestCosyFingerprintSeed_FallbackChain (0.00s)
    sign_fingerprint_test.go:94: 应优先 UID，got "fixed-seed"
FAIL
```

**正交性证明**：
- 哨兵 1（退回随机）→ 命中「幂等」+「令牌刷新不变」，**不**命中「跨账号隔离」（随机值天然隔离）
- 哨兵 2（忽略 seed）→ 命中「跨账号隔离」+「种子回退链」，**不**命中「幂等」（恒定值天然幂等）

两个断言的判别方向正交，说明测试不是单一维度的重复覆盖。

## 9. 未覆盖与残余风险

- **上游风控反应不可预测**：从随机指纹变为稳定指纹属上游可见的行为变更，无法本地验证风控反应。依据 qoderwork 0.9.41 的同款改动经验（已生产验证通过）+ 本轮 3 账号验收通过，判定为正向变化，但不作长期保证。
- **UMID 链路未纳入**：`umid.go` 已用真实远端桥稳定派生，无需改动；本轮不动该链路，避免影响已生产验证的签到能力。
- **历史英文注释未统一**：`sign.go` 中 `aesCBCEncrypt`/`jsonSortedCompact`/`buildBearer` 等历史英文注释未改写，遵循最小改动原则；定级 P3。
