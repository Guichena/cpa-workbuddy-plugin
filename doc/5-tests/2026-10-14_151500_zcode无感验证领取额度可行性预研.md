# zcode-provider 阿里云无感验证领取额度可行性预研

- 对应需求：`doc/2-需求/2026-10-14_153951_zcode支持bigmodel中国区授权需求.md`（新增诉求：插件端免客户端领取）
- 预研时间：2026-10-14
- 预研目标：验证插件面板端能否通过阿里云「无感验证」产出合法 `captchaVerifyParam`，并经 `/billing/claim` 完成 Start Plan 领取，替代「手动打开 ZCode 桌面客户端领取」
- 预研边界：只做无感验证（不做交互式滑块/点选）；只做可行性验证，不做生产改造

## 一、逆向依据（ZCode 3.15.1 app.asar）

| 项 | 事实 |
| --- | --- |
| SDK 脚本 | `https://o.alicdn.com/captcha-frontend/aliyunCaptcha/AliyunCaptcha.js`（常量 `$vn`） |
| 全局配置 | `window.AliyunRequestVerificationConfig = {region, prefix}`（init 前必须预设） |
| 初始化 | `initAliyunCaptcha({SceneId, mode, language, captchaLogoImg, showErrorTip:false, element:'#<容器>', button:'#<按钮>', getInstance, success, fail, onError})` |
| 无感路径 | `getInstance(inst)` → `inst.startTracelessVerification()`；`success(param)` 收到 `captchaVerifyParam` |
| claim 头构造 | `requestVerificationClaimHeaders = {X-Aliyun-Captcha-Verify-Param, X-Aliyun-Captcha-Verify-Region}` |
| claim 体 | `{"plan_id": "<planId>"}`，另带 `X-ZCode-App-Version` + `X-Platform` |
| planId 来源 | `getManualClaimPlanPreviews()` → `GET /api/v1/zcode-plan/billing/preview?app_version=&platform=` |
| 设备头 | `X-Device-Mid`（UUID，来自 `getDeviceMid()`），preview / claim 端点必需 |
| 服务端 captcha 配置 | `GET /api/v1/client/configs` → `data.configs.captcha = {enabled, prefix, region, sceneId, skip_model_request}` |

## 二、实测结果（生产 IP + 真实账号 + 真实浏览器）

### 2.1 无感验证可稳定产出合法参数

在真实浏览器加载 SDK，按上述契约初始化并调用 `startTracelessVerification()`，多轮测试 **100% 成功** 产出 `captchaVerifyParam`（base64，约 200+ 字符，解码含 `certifyId` / `sceneId` / `isSign` / `securityToken`）。

关键约束：**初始化必须传 `button` 元素**。缺 `button` 时上游返回 `{"success":true,"verifyResult":false,"verifyCode":"F001"}`；补齐 `button` 后立即成功。

### 2.2 参数被上游 captcha 层接受

对同一未领取账号（`zcode-6115f5c6ad614d5e`）用新鲜参数打 `POST /billing/claim`：

| region | plan_id | 上游响应 | 判读 |
| --- | --- | --- | --- |
| `sgp` | `zcode-v3-start-plan-0817` | `{"code":1003,"msg":"target already exists"}` HTTP 200 | **captcha 校验通过**（进入业务层） |
| `sgp` | `zcode-v3-start-plan` | `{"code":1001,"msg":"target not found"}` HTTP 200 | captcha 通过，plan_id 无效 |
| `cn` | 任意 | `{"code":3007,"msg":"captcha verify failed"}` HTTP 400 | captcha 未通过 |
| 无参数 | 任意 | `{"code":3007}` HTTP 400 | 对照组 |

判据：错误码由 `3007`（captcha 层）变为 `1001`/`1003`（业务层），证明 **验证头被上游完全接受**。

### 2.3 必需请求头

`preview` 与 `claim` 端点缺 `X-Device-Mid` 时返回 `{"code":3001,"msg":"parameter error"}`；补齐后返回 `code:0`。

### 2.4 参数一次性

`captchaVerifyParam` 为一次性凭证：同一参数重复提交即返回 `3007`。每次领取须重新执行无感验证。

## 三、结论

- **captcha 层可行性成立**：无感验证在浏览器环境可稳定产出被上游接受的参数，插件端无需人工干预即可越过官方人机验证。
- **端到端激活待实证**：生产 5 个账号中 4 个已激活，唯一未领取账号（`zcode-6115f5c6ad614d5e`）服务端返回 `1003 已领取过该套餐` 但 `billing/current` 返回 `plans:[]`（上游账号状态异常），无法用现有账号完成「未领取 → 已激活」的完整实证。
- **关键参数**：`region=sgp`（非上游 configs 下发的 `cn`）、`plan_id=zcode-v3-start-plan-0817`（当前插件硬编码为 `zcode-v3-start-plan`，缺 `-0817` 后缀）、必需 `X-Device-Mid`。

## 四、实施建议

1. **后端**：`claimAccountStartPlan` 修正 `plan_id` 取值；补齐 `X-Device-Mid`（进程内生成并持久化的稳定 UUID）；`captcha_required` 响应回传 `scene_id` / `prefix` / `region`（已有）。
2. **面板**：动态加载 Aliyun SDK；未领取卡片提供「领取额度」入口；流程为「调 /claim（无参数）→ 返回 captcha_required → 面板无感验证 → 带参数重调 /claim」。
3. **验证**：需一个真实未领取账号完成端到端实证后方可判定功能闭环。

## 五、未覆盖与说明

- 未做生产写操作以外的任何改造（本轮仅可行性验证）。
- 未验证面板宿主环境（CPA 管理台）能否加载外部 SDK（CSP 风险待实测）。
- 未回显任何账号凭据原值；`captchaVerifyParam` 为一次性临时凭证且不含用户身份。
