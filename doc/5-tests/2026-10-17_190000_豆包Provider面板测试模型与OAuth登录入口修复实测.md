## 一、问题 1：账号卡片缺「测试模型」

### 1.1 现象

生产面板的账号卡片只有「禁用/启用」「删除」两个按钮，无法判断账号当下是否还能出字。用户要求对齐 workbuddy 面板的「测试」能力。

### 1.2 参考实现（workbuddy）

| 环节 | workbuddy 做法 |
|---|---|
| 入口 | 卡片 `data-action="test"` → `openTestModal(auth_index)` |
| 模型列表 | `GET /models?auth_index=...` → `{models:[...]}` |
| 执行 | `POST /test-active {auth_index, model}` |
| 内核 | `sendActivePingWorkbuddy`：`stream:true, max_tokens:1`，收到首个有效输出帧立即返回 |
| 结果 | `{ok, model, elapsed, message}` / `{error, model}` |

### 1.3 豆包侧的差异与取舍

豆包的模型目录是**静态能力别名**（`doubao/default`、`doubao/pro`、`doubao/image`、`doubao/video`），不是上游动态发现，因此：

- `/models` 不需要访问上游，直接返回目录；
- **只返回文本类别名**。生图/生视频别名会让上游真正执行生成：既消耗额度又要等数十秒，且生成失败与账号不可用难以区分——活跃测试只回答「这个账号还能不能对话」。

### 1.4 实现

新增 [doubao/active_ping.go](file:///F:/cpa-plugin/doubao/active_ping.go)：

- `textModelIDs()`：从 `capabilityAliases` 过滤出 `Skill == 0` 的别名；
- `handleModelsQuery(req)`：读 `auth_index` 查询参数，缺失返回 `{error}`；
- `handleTestActive(req)`：解析 `{auth_index, model?}`，`model` 为空时取目录首项；
- `runActiveTest(sa, model)`：构造真实 `/chat/completion` 请求，逐帧解析，**首个有效输出即返回**。

首帧判定覆盖三类增量来源（与正式对话链路一致）：

| 事件 | 判定 |
|---|---|
| `FULL_MSG_NOTIFY` | 仅 `user_type=2`（助手消息）算输出，`user_type=1` 是提问回显 |
| `STREAM_MSG_NOTIFY` | 文本块非空 / 思考块非空 / 含 CREATION 块 → 成功 |
| `STREAM_CHUNK`、`CHUNK_DELTA` | `delta` / `text` / `patch_op` 文本 / 思考块 / CREATION 块 → 成功 |
| `STREAM_ERROR`、`ERROR` | 解析业务码 → **立即判失败**，不当作「有字节流出」的成功 |
| `SSE_REPLY_END` | 已结束仍无输出 → 判失败，不继续等 Keep-Alive |

`activeTestTimeout = 20s`：正常 1~3 秒返回，20 秒用于覆盖上游排队与网络抖动。

管理路由新增两条（[doubao/management.go](file:///F:/cpa-plugin/doubao/management.go)）：

```
GET  /plugins/doubao-provider/models?auth_index=<id>
POST /plugins/doubao-provider/test-active   body: {auth_index, model?}
```

面板（[doubao/panel.html](file:///F:/cpa-plugin/doubao/panel.html)）：

- 卡片新增主按钮「测试」（`data-act="test"`，带 `data-id` 与 `data-label`）；
- 新增模型选择弹窗（`.mask` / `.modal`），点模型后就地展示结果；
- 关闭弹窗或切换账号时丢弃迟到响应（`testAuthID !== id` 守卫），避免错投；
- 测试进行中禁用模型按钮，结束后恢复。

## 二、问题 2：OAuth 登录无法使用

### 2.1 现象

宿主「+ 添加账号」弹窗显示：`认证失败: failed to generate authorization url`。

### 2.2 根因

该文案不是插件产出，而是宿主统一兜底。调用链（宿主源码 `v7.2.129`）：

```
GET /v0/management/doubao-provider-auth-url
  → ServePluginAuthURL
    → host.HasAuthProvider("doubao-provider")   // true：插件声明了 auth_provider
    → host.StartLogin(...)
      → plugin.auth.login.start                  // 插件未实现 → unknown_method
    → errStart != nil
  → 500 {"error":"failed to generate authorization url"}
```

关键事实：`supports_oauth` 由 `Capabilities.AuthProvider != nil` 决定。插件声明了 `AuthProvider: true`，却只实现了 `auth.identifier`，于是宿主把「+」指向本插件、再在 `auth.login.start` 上失败——**声明与实现不匹配**。

生产实测复现（修复前）：

```
GET /v0/management/doubao-provider-auth-url
→ {"error":"failed to generate authorization url"}  HTTP 500
```

宿主插件列表同时显示 `supports_oauth: true, oauth_provider: "doubao-provider"`，与用户界面上的「+」一致。

### 2.3 方案选择

豆包没有可接入的授权码流程：登录态是浏览器侧的 HttpOnly Cookie（`sessionid`、`sessionid_ss`、`sid_tt`、`sid_guard`、`ttwid` 等），页面 JS 读不到，只能由用户从浏览器导出。这与既定的认证路线一致（复用用户浏览器登录态，插件内不实现登录）。

因此不实现「一键授权」，而是把宿主弹窗变成**引导页桥接**（与 copilot / traework 的桥接页同一模式）：

```
用户点「+」→ 宿主打开桥接页（resource 路由，免管理密钥）
  → 页面引导：浏览器登录豆包 → 复制 Cookie → 粘回页面
  → 页面 POST /import（带 management key）
  → 插件校验并落盘
  → 宿主轮询 auth.login.poll → 发现新账号 → 完成
```

### 2.4 实现

新增 [doubao/login.go](file:///F:/cpa-plugin/doubao/login.go)：

| 方法 | 行为 |
|---|---|
| `auth.login.start` | 登记会话（`state` + 起始时间 + 账号基线），返回桥接页相对 URL |
| `auth.login.poll` | 账号集合出现新成员，或已有账号 `UpdatedAt` 晚于会话开始 → `success` + `AuthData`；否则 `pending`；会话过期 → `error` |
| `auth.parse` | 认领 `doubao-*.json` 且含 `cookie_header` 的文件；其它交回宿主 |
| `auth.refresh` | 原样返回现有凭据并把下次刷新推远 24 小时（豆包无法自助续期） |
| `GET /login` | 渲染桥接页（resource 路由） |

**防假成功**：成功判据只用插件自己写入的 `UpdatedAt` 与 `authID` 基线，**不使用宿主 `HostAuthFileEntry.CreatedAt`**——插件刷新存量账号也会重置该时间戳，用它判成功会在用户尚未粘贴时误报完成。

**结果只消费一次**：`success` 后立即删除会话，同一 `state` 二次轮询返回「会话不存在或已过期」。

桥接页的 management key 获取与面板同款三段式（父窗口 localStorage 解密 → 手动输入 → sessionStorage），401/403 时清 key 并提示重填。

## 四、0.1.3 追加修复：OAuth 轮询假成功

### 4.1 问题

0.1.2 生产浏览器验收时发现：用户**完全没有粘贴 Cookie**，`GET /v0/management/get-auth-status?state=<state>` 也会返回 `success`。

### 4.2 根因

原判据是 `findFreshAccount`：只要「账号 authID 不在登录会话开始时的基线集合里」**或**「`UpdatedAt` 晚于会话开始时间」就判成功。但 Cookie Jar 每次请求后都会把滚动 Cookie 回写账号文件，回写会刷新 `UpdatedAt`——于是任意一次面板操作（如点「测试」）都能把旧账号刷成"新账号"，触发假成功。

### 4.3 修复

- `loginSession` 改为只认显式信号 `importedAuthID`；
- 新增 `markLoginImported(state, authID)`，仅当 `/import` 请求体带 `login_state` 且导入成功时登记；
- 删除 `findFreshAccount` / `mustParseTime` / `currentAuthIDSet`，新增 `findAccountByID`；
- 桥接页提交体改为 `{cookie, label:"", login_state: STATE}`；
- 登录会话已过期但账号已落盘时返回 `ok:true` + 提示，不丢账号。

### 4.4 验证

| 层级 | 手段 | 结果 |
|---|---|---|
| 单测 | `TestPollLoginIgnoresRefreshedAccounts`：先写历史账号 → start login → 模拟 Cookie 回写刷新 `UpdatedAt` → poll | `pending`（通过） |
| 变异自测 | 把判据改回「任意账号即成功」 | 断言失败并报出实际值 `success`，证明测试有效 |
| 生产只读 | `get-auth-status` 连续 3 次（未导入） | 全部 `{"status":"wait"}` |
| 生产关键路径 | 新会话 → 先跑一次 `/test-active` 触发 Cookie 回写刷新 `UpdatedAt` → 再轮询 3 次 | 全部 `{"status":"wait"}`，假成功已消除 |

## 六、遗留与边界

1. **上游限流未解除**：`710022004 rate limited`（`shark_admin/verify/semantic_reasoning`）是账号级风控，与本次改动无关；测试按钮会如实把它显示为失败。
2. **桥接页未做"粘贴 Cookie 后自动关闭"的完整生产闭环**：生产账号 Cookie 需用户从浏览器手工导出（Chrome 的 App-Bound Encryption 使程序化导出不可行），本轮验证到「桥接页可用 + 导入接口契约正确 + 轮询不再假成功」为止；真实新账号导入需用户本人粘贴。
3. **device_id / web_id 未持久化**（既有缺口，本轮未修）：`saveCredentials` 未写入 `DeviceID` / `WebID` / `WebTabID`，业务 query 里这三项为空串。与本轮两个问题无因果关系，建议单独立项。
4. **CI 的 FreeBSD 交叉编译不稳定**：`copilot-provider freebsd-amd64` 的 `base.txz` 下载连续失败，会阻塞任何插件的 Release 步骤，建议后续单独治理（镜像重试或改用更稳定的分发源）。
