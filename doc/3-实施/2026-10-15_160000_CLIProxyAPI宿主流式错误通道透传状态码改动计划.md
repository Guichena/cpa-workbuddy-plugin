# CLIProxyAPI 宿主改动计划：流式错误通道透传数字状态码

- 计划编号：PLAN-HOST-STREAM-STATUS-CHANNEL-20261015
- 提出时间：2026-10-15（北京时间）
- 目标仓库：**CLIProxyAPI**（`F:/CLIProxyAPI`，独立仓库，remote `luode0320/CLIProxyAPI`）
- 来源 Bug：`doc/4-bugs/2026-10-15_160000_Qoder排队帧被误判账号级故障且跨provider状态码通道缺失根因诊断.md`（本仓库 cpa-plugin）
- 状态：**计划待执行**（本仓库跨项目写入红线要求：只能在 CLIProxyAPI 仓库另开会话实施）

## 1. 为什么必须改宿主

插件侧已让排队帧失败信封携带 `http_status:503`（cpa-plugin 本轮改动），但这只覆盖**非流式**与**同步流式**两条路径——它们经 RPC 失败信封返回，宿主 `decodeEnvelopeResult` 会读 `Error.HTTPStatus`。

**生产流式请求走的是异步路径**：插件 `handleExecStream` 拿到 `StreamID` 后立即返回，后续由 `pumpUpstreamStream` 用 `host.stream.emit` 推送。错误经该通道传输时：

1. 插件侧 `streamEmitError` → `host.stream.emit` 的 `error` 字段（字符串）；
2. 宿主 `callHostStreamEmit`（`internal/pluginhost/host_callbacks.go:381-394`）把字符串包成 `fmt.Errorf("%s", req.Error)` —— **纯文本，无结构**；
3. 该 `chunk.Err` 经 `stream_bridge.go` → `adapters_executors.go` → conductor；
4. conductor `statusCodeFromError`（`sdk/cliproxy/auth/conductor_cooldown.go:1448`）只认 `StatusCode() int` 接口，纯文本恒得 **0**；
5. `isCredentialRetryRoundStatus(0)` = false ⇒ **跨 provider 轮转永不触发**。

**结论**：插件侧无论怎么改，异步流式路径的状态码都带不出来。必须在宿主侧让 `host.stream.emit` / `host.stream.close` 支持结构化错误详情。

**关键落差**：非流式路径有 `rpcError.StatusCode()`，流式路径没有等价物。

## 3. 建议改法（最小改动、不动 ABI 版本）

### 3.1 扩展两个 RPC 请求结构（向后兼容）

`stream_bridge.go`：
```go
type rpcStreamEmitRequest struct {
	StreamID string `json:"stream_id"`
	Payload  []byte `json:"payload,omitempty"`
	Error    string `json:"error,omitempty"`
	// HTTPStatus 是插件对失败语义给出的数字状态码；0 表示未提供。
	HTTPStatus int `json:"http_status,omitempty"`
}

type rpcStreamCloseRequest struct {
	StreamID   string `json:"stream_id"`
	Error      string `json:"error,omitempty"`
	HTTPStatus int    `json:"http_status,omitempty"`
}
```

字段可选、缺省为 0，**旧插件不受影响**（omitempty + 缺省零值语义一致），故无需提升 `pluginabi.ABIVersion`。

### 3.2 让错误携带状态码

新增一个实现 `StatusCode() int` 的错误类型（与 `modelExecutionStatusError` 同形，`host_callbacks.go:465-486` 已有可复用范式）：
```go
type streamStatusError struct {
	message    string
	statusCode int
}

func (e *streamStatusError) Error() string   { return e.message }
func (e *streamStatusError) StatusCode() int { return e.statusCode }
```

在 `callHostStreamEmit`（`host_callbacks.go:386-389`）与 `streamBridgeStream.run` 的 close 分支（`stream_bridge.go:100-102`）中：`HTTPStatus > 0` 时用 `streamStatusError` 包壳，否则保持 `fmt.Errorf("%s", ...)` 原行为。

### 3.3 校验点

- `statusCodeFromError`（`conductor_cooldown.go:1448`）会经 `errors.As` 命中 `streamStatusError.StatusCode()` → 得到 503 → `isCredentialRetryRoundStatus(503)=true` → 触发跨 provider 轮转。
- 注意 `MarkResult`（`conductor_cooldown.go:855-862`）对 403 打 30 分钟冷却、对 503（`:949`）打瞬时冷却（默认 1 分钟）。**插件侧已选 503**，此处无需特殊处理；但若未来有插件对排队报 403，会误伤 30 分钟冷却。

## 4. 验证方式

1. **单元测试**（宿仓库内）：
   - `callHostStreamEmit` 传 `http_status:503` → 断言 `chunk.Err` 满足 `interface{ StatusCode() int }` 且值为 503；
   - `http_status` 缺省 → 断言旧行为（纯文本错误、`StatusCode()` 得 0）；
   - `host.stream.close` 同款两条断言。
2. **集成断言**：构造 `statusCodeFromError(streamStatusError{statusCode:503})` 返回 503；`isRequestRetryRoundError` 返回 true。
3. **端到端（可选）**：在 cpa-plugin 侧让某 provider 对流式请求返回带 503 的排队错误，观察宿主日志是否出现跨 provider 轮转（`selector.go` 的 provider 切换记录）。

## 5. 风险与边界

- **不提升 ABI 版本**：字段可选且缺省语义与旧行为一致；若宿主与插件版本错配，旧插件发出的报文不含该字段，宿主按 0 处理，等价于现状。
- **仅影响流式失败语义**：非流式路径已可用，无需改动。
- **需与 cpa-plugin 侧联动**：插件侧 `streamEmitError` 目前只发字符串。若要让异步流也带 503，插件侧需同步在 `streamEmitError` 路径补 `http_status` 字段（本轮插件改动已覆盖信封路径，异步 emit 路径可作后续增量）。
- **不在本会话实施**：CLIProxyAPI 是独立仓库，按 cpa-plugin 仓库的跨项目写入红线只读；本计划仅供在 CLIProxyAPI 仓库另开会话执行。
