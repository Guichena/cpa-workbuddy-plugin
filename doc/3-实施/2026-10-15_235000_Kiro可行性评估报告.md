# Kiro (AWS) 插件立项可行性评估报告

- 评估时间：2026-10-15
- 评估性质：**可行性评估，非实现**（CYCLE-5）
- 评估对象：是否为 AWS 的 AI IDE「Kiro」开发 CPA（CLIProxyAPI）第三方 Provider 插件
- **最终建议：不立项**

## 一、结论摘要

| 维度 | 判定 | 依据强度 |
|---|---|---|
| 技术可行性 | 可行（中高档难度） | 有据可查 |
| 免费额度价值 | **极低**（50 credits/月） | 官方一手 |
| 合规风险 | **高**（ToS 明文禁止） | 官方一手 |
| 封号风险 | **高**（已有真实批量封禁案例 + 指纹/IP 绑定） | 有据可查 |
| **综合建议** | **不立项** | — |

**核心判断**：技术上能实现，但 ToS 明确禁止「第三方自动化 harness 绕开 Kiro 原生接口」，且已有真实封禁案例与设备指纹/IP 绑定机制。免费档每月仅 50 credits，经济价值极低。**风险与收益严重不匹配**，建议不立项。

## 二、免费额度与经济价值（官方一手）

Kiro 计价单位为 **credits**（非早期文档所称 "agentic requests"），每计费月重置、不结转：

| 档位 | 价格（USD/月） | 额度 |
|---|---|---|
| Free | $0 | **50 credits** |
| Pro | $20 | 1,000 credits |
| Pro+ | $40 | 2,000 credits |
| Pro Max | $100 | 5,000 credits |
| Power | $200 | 10,000 credits |

- 加量包 $0.04/credit，最低 $5。
- 计量精确到两位小数，最小 0.01 credit。
- 不同模型消耗倍率不同（如 Sonnet 4.6 为 Auto 的 1.3 倍）。
- **无独立 API 额度**：订阅额度由 IDE / CLI / Web / Crew / ACP 共用同一池，「无论工作跑在哪个接口都消耗同一份 credits」。

**经济价值评估**：免费档 50 credits/月，按「复杂 spec 任务通常超过 1 credit」的口径，实际可用请求数量级为**数十次/月**。与 GitHub Copilot 免费档（实测可发现 57 个模型、完成长对话推理）相比，价值差距显著。

## 三、合规风险（官方一手，决定性因素）

### 3.1 ToS 明文禁止

Kiro 官方 FAQ 原文（已直接核验）：

> Use through third-party automation harnesses (such as OpenClaw) that route requests outside of Kiro's native interfaces **is not permitted**.

定价页亦重申第三方自动化「not permitted」。许可依据为 AWS Customer Agreement + AWS Service Terms。

**这条直接命中本插件形态**：CPA Provider 的本质就是把上游额度经非官方接口转出，属条款明确禁止的行为。

### 3.2 真实封禁案例

社区记录（OmniRoute #9216，含 #649 / #2026）：批量导入 Kiro 账号后出现 `All connections banned by upstream`，上游判定为**终局封禁、一年冷却**。

触发信号：
- IP / 设备指纹与 Kiro IDE 不一致；
- 导入后突发流量；
- 批量加号。

解封途径：联系 AWS 支持 + 用官方 IDE 登录一次（侧面印证存在指纹校验与人工审核环节）。

### 3.3 设备指纹绑定

封禁判据为「与 IDE 不同的 IP / fingerprint」，说明存在指纹校验机制；MITM 模式可保留原指纹（从反面印证该机制真实存在）。

## 四、技术可行性（供记录，不影响结论）

即便不考虑合规，技术上确实可行：

| 项 | 事实 |
|---|---|
| 后端基础设施 | 复用 Amazon Q Developer / CodeWhisperer：`codewhisperer.{region}.amazonaws.com`、`q.{region}.amazonaws.com`，新版为 `runtime.{region}.kiro.dev` |
| 推理接口 | `GenerateAssistantResponse`（`X-Amz-Target: AmazonCodeWhispererStreamingService.GenerateAssistantResponse`） |
| 请求体格式 | **JSON**（非 protobuf），CodeWhisperer 专有结构 `conversationState{currentMessage.userInputMessage, history}` |
| 鉴权 | **Bearer token**（未发现推理路径需 SigV4） |
| 响应格式 | AWS eventstream **二进制事件流**，需自行解析 |
| 指纹伪装 | 必需：User-Agent 须含匹配的 `AppVersion` / `KiroVersion`，否则被拒 |
| 登录形态 | 5 种（GitHub / Google / AWS Builder ID / IAM Identity Center / 外部 IdP SSO）；无固定 public client_id，需从 kiro-cli 的 OIDC 动态注册产物中取 |

**实现难度：中高档**，明显高于 GitHub Copilot（纯 Bearer + REST + OpenAI 格式）。主要难点：
1. 构造 CodeWhisperer 专有 JSON 体并做双向格式翻译；
2. 解析 AWS eventstream 二进制事件流；
3. 必须伪装 `KiroVersion` / 机器码 / User-Agent；
4. 多账号 refresh token 生命周期管理。

**既有可参照实现**（若未来重新评估）：
- `Quorinex/Kiro-Go`（MIT，活跃，~1.2k star）
- `aliom-v/KiroGate`（AGPL-3.0，**已归档** 2026-06-19）
- `jwadow/kiro-gateway`（AGPL-3.0，206 commits）
- `hueyexe/open-kiro`（MIT，Go）
- `Colin3191/kiro-proxy`（读 `~/.aws/sso/cache/kiro-auth-token.json`）

注：`tashfeenahmed/freellmapi`（34 个 provider 的聚合项目）**不含 Kiro**。

**待实测澄清项**（若立项才需处理）：
- SigV4 的缺席是基于多个逆向项目文档「未提及 + 明示 Bearer」，非服务端抓包直证；管理类 API（如 `user-subscriptions.us-east-1.amazonaws.com/ListUserSubscriptions`）实测需 SigV4。
- 免费档 client_id 是否可跨账号复用。
- 推理端点是否有速率/指纹二次校验。

## 五、立项建议

### 明确建议：**不立项**

理由（按权重排序）：

1. **合规红线**：ToS 明文禁止第三方自动化绕开原生接口。本插件形态直接命中，属条款禁止行为；即便用户自行承担风险，仓库维护者仍会因分发该插件承担连带声誉与法律风险。
2. **封号风险已实证**：批量导入 + 指纹/IP 不一致会导致终局封禁（一年冷却），且解封需人工联系 AWS 支持。这会造成真实用户账号损失。
3. **收益极低**：免费档 50 credits/月，可用请求数量级为数十次/月，远低于同类插件（Copilot 免费档可长对话推理）。投入产出比不成立。
4. **实现成本高**：CodeWhisperer 专有协议翻译 + AWS eventstream 二进制解析 + 版本指纹伪装，工作量显著高于既有 Copilot 插件。

### 若未来重新评估的前置条件

- AWS 官方明确放开第三方客户端/API 接入（如正式提供 API Key 供第三方 harness 使用）；
- 或免费档额度提升至具备实际使用价值（如数百 credits/月以上）；
- 且届时需先做一次真实请求头实测，澄清 SigV4 与指纹校验的准确边界。

### 与既有项目的对比结论

| 项目 | 免费额度 | ToS 态度 | 结论 |
|---|---|---|---|
| GitHub Copilot | 可用（57 模型） | 未明文禁止第三方客户端 | **已立项并发布 0.1.0** |
| OpenCode | 免费模型被指纹闸门封死 | — | 已裁定暂停立项 |
| **Kiro** | 50 credits/月 | **明文禁止** | **不立项** |

## 六、诚实边界

- 本报告为**桌面调研**，未对 Kiro 发起任何真实请求，未注册账号，未做抓包实测。所有技术细节来自公开文档与第三方逆向项目源码/文档。
- 合规判断依据为 Kiro 官方 FAQ 与定价页的**原文表述**（已直接核验），但未取得 AWS 法律意见；实际执行尺度可能随 AWS 政策变化。
- 封禁案例来自社区讨论记录，未能独立复现；「一年冷却」为该案例的具体数值，不代表普遍规律。
- 未评估「用户自行部署、仓库不公开分发」这一形态下的风险差异。
