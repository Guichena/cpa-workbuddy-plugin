# copilot 宿主 OAuth 弹窗设备码桥接页实施总览

- 编号：IMPL-COPILOT-HOST-OAUTH-BRIDGE-20261016
- 触发：用户裁定（2026-10-15）采纳「选项 B：改造 handleStartLogin 返回插件自有 resource 前缀的桥接页」
- 状态：进行中

## 1. 当前计划最终方案简要说明

`copilot-provider` 的宿主 OAuth 弹窗（管理台「登录」卡片）当前**不显示 GitHub 设备码**，因为宿主 `ServePluginAuthURL` 把插件返回的 `AuthLoginStartResponse.Metadata` 只写进宿主 session store、不回传前端（宿主源码硬编码响应为 `{status, url, state}`）；而宿主内置 provider 把 `user_code` 放响应顶层所以能显示。**本方案不依赖宿主改动**（宿主前端 HTML 不在本仓库、无法就地修补），改为让插件 `handleStartLogin` 返回**插件自有 resource 前缀的桥接页相对 URL**，由该页显示设备码 + 授权链接 + 自动轮询 —— 宿主弹窗打开的即该页，用户直接看到码。该模式在 `traework/login.go` + `traework/browserlogin.go` 已有生产验证过的先例。

## 2. agent 对问题的理解

- **问题/目标**：宿主通用 OAuth 弹窗拿不到设备码，用户无法完成 GitHub Device Flow 授权；需要让用户在弹窗打开的页面上**直接看到设备码**并完成登录，且不依赖宿主改动。
- **本轮范围**：`copilot/` 插件内新增桥接页路由与页面渲染；改造 `handleStartLogin` 返回桥接页 URL；`handlePollLogin` 保持不变（仍是宿主轮询入口）；面板流程 `/login-start` `/login-poll` 保持不变；单测补齐；版本与 CHANGELOG。
- **非范围**：宿主 CLIProxyAPI 任何改动（跨项目只读红线）；GitHub Device Flow 协议本身（`requestDeviceCode` / `pollAccessToken` / `settleDeviceLogin` 全部复用）；面板 `panel.html` 的登录交互（已能显示码，不动）；`upstream.go` 指纹头；多账号机制。
- **当前优先闭环**：`python scripts/cgo-shim-build.py copilot` build/vet/test 全绿 + 桥接页 HTML 真实渲染断言通过 + 宿主弹窗路径（`handleStartLogin` 返回相对 URL）断言通过。
- **关键假设**：
  1. 宿主把插件 `AuthLoginStartResponse.URL` 原样交给前端 `window.open`，相对路径在管理域 origin 下解析正确（traework 0.1.45 已在生产验证此假设）。
  2. GitHub 对该 `client_id` **不返回** `verification_uri_complete`（本轮已 curl 实测：字段仅 `device_code`/`expires_in`/`interval`/`user_code`/`verification_uri`），因此桥接页必须**显示设备码让用户手输**，不能走「预填链接一键直达」的简化路线。
  3. resource 前缀 `/v0/resource/plugins/<id>/...` 由宿主 `pluginResourceNoRoute` 分发到插件 `ManagementHandle`，是插件唯一免鉴权的 GET 面（traework 已生产验证）。

## 3. 关键耦合（必须一并处理）

1. **宿主 `ServePluginAuthURL` 的契约缺陷不可绕过**：它只回 `{status, url, state}`，插件 Metadata 里的 `user_code` 永远到不了前端。唯一出路是让「URL 本身」就是能显示码的页面 —— 即桥接页。
2. **`handlePollLogin` 必须保持宿主语义**：宿主 `GetAuthStatus` 调 `host.PollLogin` → 插件 `handlePollLogin` 返回 `AuthLoginPollResponse`（含 `Auth` 记录），宿主持久化凭据文件。桥接页只负责**展示与触发**，不落盘（与 traework 的 `hostPersists` 语义一致）。copilot 现有 `settleDeviceLogin` 已直接落盘账号 —— 这是面板路径的既有行为，**本轮不改**，桥接页复用同一 `pollDeviceLogin`，由宿主轮询触发落盘。
3. **桥接页与面板共享同一 `oauthSessions` 会话表**：桥接页与面板 `/login-start` 都调 `startDeviceLogin()`，state 存在同一个 `sync.Map`。桥接页只做「显示 + 轮询驱动」，不新增第二套会话状态。

## 5. 验证步骤与通过标准

- **真实测试入口**：`python scripts/cgo-shim-build.py copilot`（build + vet + test），全绿。
- **哨兵反证**：临时把桥接页 `user_code` 渲染去掉，确认新增断言精确 FAIL；恢复后全绿。
- **桥接页 HTML 校验**：Go raw string 内**不得出现反引号**（会截断）；断言 HTML 含 `user_code` 值与 `verification_uri`。
- **面板回归**：`node --check` 校验 `panel.html` 内联 JS 语法 + `test/copilot/panel_render_repro.mjs` 真实执行（确认本轮未破坏面板）。
- **通过标准**：cgo-shim all green；哨兵精确 FAIL 后恢复；`handleStartLogin` 返回相对桥接页 URL 断言通过；面板回归 PASS；`POLLUTION: PASS`；`STYLE: PASS`。

## 6. 任务完成条件 / 停止条件 / 最大推进边界

- **完成条件**：桥接页可在宿主弹窗内显示设备码并驱动轮询；`handleStartLogin` 返回相对 URL；单测全绿；版本与 CHANGELOG 收口。
- **停止条件**：cgo-shim 无法运行（环境缺 C 工具链且 WSL 不可用）时，降级为静态验证并明确交接；出现跨项目写入需求时立即停止（红线）。
- **最大推进边界**：只改 `copilot/` 内文件 + 本实施文档 + 测试文档 + 6-review；**不碰宿主 CLIProxyAPI**；不改面板登录交互；不改 Device Flow 协议内核。

## 7. 风险与回退

- **风险 1**：宿主前端可能对插件返回的 URL 做绝对化处理或只接受 `https://`。缓解：traework 0.1.45 已用同一相对路径模式在生产验证通过，风险低；若生产验收发现弹窗打开异常，回退为返回 `verification_uri` 并在 Metadata 补码（恢复本轮前行为），面板路径不受影响。
- **风险 2**：桥接页自动轮询频率过高触发 GitHub `slow_down`。缓解：轮询间隔取会话 `Interval`（默认 5s，与面板一致），仅在页面可见时轮询。
